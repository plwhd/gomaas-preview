UI 组件库的形成：从重复设计到共同维护界面

发布于 2026.11.13AI 辅助：GPT

关键词：UI 组件库　·　设计系统　·　界面复用　·　设计协作　·　Ant Design　·　Arco Design

This article is available in Chinese.

打开一个企业后台，页面可能分别管理订单、客户、库存和财务，但组成它们的界面元素往往十分相似：顶部是查询条件，中间是表格，旁边或下方放着新增、编辑、导出等操作。业务内容不断变化，输入框、按钮、弹窗和分页却反复出现。

UI 组件库就从这种重复中获得了存在的理由。团队把可以反复使用的界面单元及其规则集中维护，让不同页面调用同一套资源。它改变了设计工作的组织方式：过去需要在每个页面重新决定、反复解释的事情，有一部分可以提前形成约定。

但从“复制一个按钮”到“维护一套组件库”，中间还隔着外观、行为、代码和团队协作。理解这段发展过程，才能判断组件库究竟解决了什么，以及为什么已经有了 Ant Design、Arco Design，产品团队仍然会有自己的组件工作。

一、重复出现的界面，开始需要共同规则

假设三个小组分别设计订单、客户和库存页面。最初，各自决定按钮高度、表单间距和弹窗宽度，似乎没有什么问题；页面不多，差异也可以靠沟通修正。

随着功能增加，同一个“保存”可能出现几种表现：有的提交后立即关闭弹窗，有的显示加载状态，有的允许连续点击，有的失败后清空已经填写的内容。差异开始影响用户对操作结果的判断，也增加测试和修复的工作。

这里有两类重复。第一类是生产过程的重复：相似的东西被反复画、反复写、反复检查。第二类是决策的重复：每个团队都重新回答某个状态怎样表达、某种错误怎样处理。只复制外观，可以减少第一类劳动，却未必能消除第二类分歧。

组件化的关键，是找出哪些决定可以共同使用，哪些差异需要留给具体业务。 一旦共同部分有了稳定边界，页面设计就可以把更多精力放在信息关系、任务流程和特殊情境上。

二、从系统控件到网页工具包：复用早于开源组件库

界面复用并不是 Ant Design 或 React 出现后才产生的想法。桌面软件的操作系统和开发工具早已提供按钮、文本输入、列表等控件。Windows 的官方文档将控件描述为供应用接收输入、选择选项、触发操作或显示状态的界面元素，同时提供相应的编程接口。[1]

这类机制把一部分基础能力交给平台处理。应用开发者可以调用已有控件，而不必为每一个输入框重做文字编辑、焦点和事件响应。用户也能够在不同软件之间遇到相对熟悉的操作。

网页同样有原生按钮、输入框和选择框，但一个完整产品还需要处理页面布局、视觉样式，以及原生元素没有直接提供的复杂组合。团队可以自行编写这些内容，也可以复用别人整理好的工具包。

Bootstrap 是其中一个有清楚记录的案例。它在 2010 年中期诞生于 Twitter，早期名称是 Twitter Blueprint，在 2011 年 8 月公开发布之前，已经用于内部工具的样式指导。共同创建者 Mark Otto 的十周年回顾进一步说明：他负责广告产品设计，Jacob Thornton 负责内部工具开发，两人的合作与广告管理工具的建设有关。[2][3]

这个起点很有代表性：相似界面的集中维护，来自具体的交付需要。布局、排版和基础交互有了共同起点，新页面便不必从空白开始。

不过，Bootstrap 不能被当作所有组件库的共同祖先。桌面控件、网页工具包和后来的前端组件，在不同技术环境下回应着相关问题；它们并没有形成一条所有团队依次走过的升级路线。

三、从样式集合到可组合的界面单元

共享样式可以让按钮看起来一致，却不能独自决定按钮怎样响应操作。随着网页应用承担更多任务，复用的对象也开始包含结构和行为。

以 React 为例，它允许开发者将界面的结构、样式和交互逻辑组织为可复用的组件，再把组件组合成页面。组件可以接收不同内容和配置，因此同一套实现可以用于多个位置。[4]

例如，一个“保存”按钮可以接收文字、是否加载、是否禁用以及点击后执行什么操作。按钮本身负责规定的展示和交互，业务页面决定要保存哪一条记录。共同部分与业务部分因此有了可辨认的接口。

但代码被封装起来，并不意味着它已经适合共享。假设把订单状态、仓库权限和某个页面的跳转规则全部塞进一个“通用按钮”，其他业务使用时就必须理解与自己无关的逻辑。组件虽然名义上通用，实际却越来越难修改。

因此，组件库的发展不只是把更多代码收进同一个目录，也包括对复用边界的持续判断：输入、输出和状态怎样约定；哪些功能由组件承担；哪些内容由页面传入。这些边界直接决定了组件能服务多少场景，以及一次修改会影响多少地方。

四、Ant Design 与 Arco Design：从企业产品中抽取共同部分

企业软件尤其容易产生组件库需求。订单、审批、客户管理等页面虽然对象不同，却大量使用表格、表单、筛选和反馈；同时，权限、状态和数据变化又让这些单元比静态展示复杂。

Ant Design 的官方介绍直接交代了它的背景：企业级产品数量多、功能复杂、变化频繁，其中存在大量相似页面和组件，团队因而从项目实践中抽取稳定、可复用的内容，形成设计体系。[5]

这说明它所积累的不只是外观选择，也有对一类产品问题的处理经验。例如，表格需要容纳哪些操作，表单错误怎样关联到字段，弹窗中怎样组织确认与取消。具体约定仍需查阅相应文档，但把这些对象放在同一套体系中，已经减少了团队逐项重新协调的范围。

Arco Design 也体现了从基础组件向配套资源扩展的做法。其官方 React 仓库除了代码组件，还列出 Figma 组件资源、主题配置平台和可复用业务物料等入口。[6]

两者都可以作为企业界面建设的起点，但不能仅凭组件数量判断适配程度。一个日期选择器能否处理所需的日期范围，一个表格能否支持实际的数据操作，往往比它默认的圆角是否符合偏好更重要。组件库中沉淀了原有场景的选择，使用者需要辨认这些选择与自己的业务是否一致。

设计系统实践也把范围扩展到了跨产品、跨机构的协调。2014 年公开亮相的 Material Design 尝试将视觉语言带到不同设备；2015 年建立的美国网页设计系统 USWDS，则服务于政府数字服务团队。它们说明，共同维护界面的需求可以出现在不同组织中，并不只属于互联网企业后台。[7][8]

这些案例可以帮助理解发展方向：基础复用逐渐与视觉原则、使用指导、开发资源和维护机制连接起来。不同体系的范围和侧重点各不相同，不能简单排成“谁更高级”的次序。

五、设计组件与代码组件：同一个约定的两种表达

UI 工作中经常同时出现“设计组件库”和“研发组件库”。两者服务于不同工作环境，但需要围绕同一组约定协作。

设计组件通常存在于 Figma 等工具中，用于表达尺寸、排版、变体和状态。以 Figma 为例，主组件定义属性，实例在不同设计位置复用，并与主组件保持关联；组件也可以通过团队库共享。[9]

代码组件则运行在实际产品中。它需要接收真实输入、响应操作、处理焦点，并与浏览器和业务代码配合。设计图里的一种错误状态，在产品里还需要解决何时出现、怎样被辅助技术识别、修正后如何消失等问题。

同一对象 设计组件主要表达 代码组件主要实现
按钮 强调层级、尺寸、文字与状态外观 激活操作、加载与禁用、焦点及事件响应
输入框 标签、内容、帮助信息和错误的关系 输入与校验接口、状态更新、可访问名称
弹窗 内容布局、操作位置和不同状态 打开关闭、键盘操作、焦点进入与返回

这张表用于说明职责关系，不代表所有团队采用完全相同的分工。

以按钮为例，W3C 的无障碍实践指南除了描述其用途，还说明了键盘激活和操作后的焦点去向。触发弹窗时，焦点需要进入相应情境；关闭后，也需要有合理的返回位置。[10] 这些行为不能从一张按钮截图中自动得到。

所以，设计组件与代码组件不要求图层结构和代码结构一一相同，但名称、用途、状态及关键行为应当能够相互对应。如果设计稿允许某种组合，代码却不支持；或者线上产品已经改变，设计库还停在旧版本，组件库便会重新成为沟通障碍。

六、组件库、设计规范与设计系统的关系

这几个词在实际工作中经常混用，可以按照它们解决的问题来区分。

设计规范记录规则，例如正文与标题的关系、颜色如何使用、错误信息怎样表达。组件库把部分规则组织成可以直接调用的设计资源或代码。设计系统进一步连接原则、组件、使用指导、工具和维护流程，使团队能够持续采用这些约定。

这不是三个必须依次获得的资格。一份小型产品的组件库也可以附有清楚的规范；大型设计系统也可能存在尚未覆盖的业务场景。名称没有替代实际内容。

组件怎样组合，也是体系中的重要部分。一个输入框和一个按钮可以组成搜索区域，但搜索何时触发、没有结果时显示什么、筛选是否保留，仍需要额外决定。Brad Frost 的原子设计方法，用基础元素、组合单元、较复杂区域、模板与页面来描述这种相互联系。[11]

这套方法提供了一种观察尺度：既能看到单个控件，也能回到完整页面检查组合效果。它不意味着每一个产品都必须建立五层目录，更不意味着把界面拆得越细，设计就越成熟。

七、组件库建好之后，维护才真正开始

假设团队统一修改了输入框的高度，设计库中可能只需调整主组件，但真实影响会沿着多个方向扩散：紧凑表格中的编辑区域是否还能容纳，弹窗是否变长，移动端是否需要更多滚动，原来的对齐是否仍然成立。

共享提高了修改效率，也扩大了错误的传播范围。因此，组件库需要有使用文档、版本记录、验证范围和明确的维护责任。调用了同一个组件，不等于每个项目都已经升级到同一个版本；更新发布之后，仍可能需要迁移和复核。

Atlassian 的贡献说明把代码错误、Figma 组件问题和文档问题放在同一套维护范围内，并指出较大功能变动需要协调代码、设计与指南。[12] 这表明维护对象并不限于某个文件，而是一组需要彼此一致的约定。

新组件进入共享库，也应当有门槛。GOV.UK 设计系统要求提案证明其对多个团队或服务有用，并且不重复已有方案；发布前还要检查可用性、一致性，以及在不同情境、设备和辅助技术中的适用情况。[13]

这些要求有实际原因：一个只服务某个项目的特殊模块，一旦进入公共库，其他人便会期待它有文档、有支持、能升级。共享范围越大，维护承诺越重。保留少量明确的业务例外，有时比扩大公共组件更容易持续。

八、成熟组件库之后，产品团队仍然需要做的工作

使用现成组件库，通常可以节省基础控件的实现和维护投入，但产品仍需要决定哪些信息先出现、哪些操作组合在一起，以及用户遇到错误后怎样继续。这些问题依赖具体业务，通用组件无法代替团队作出全部判断。

例如，假设一个素材管理产品采用成熟组件库的按钮、输入框和弹窗。它仍需要设计“素材卡片”：预览图、名称、处理状态、作者和操作怎样排列；多选之后哪些动作允许批量执行；上传失败时能否单独重试。这一层可以复用基础组件，同时形成自己的业务组件与流程规则。

对已有库的调整，也有不同程度。只改变主题颜色，与改变组件内部结构，维护负担不同；在已有接口之外反复覆盖内部样式，可能让后续升级变得困难。团队需要先判断现有能力能否满足要求，再决定配置、组合、扩展或独立实现。

因此，组件工作可以从实际重复最多、规则最稳定的地方开始。初期只有少数页面的产品，可能先统一文字、颜色和几个高频控件就足够；需求仍在快速探索时，也可以把特殊方案留在局部，等重复需求出现后再决定是否提升为共享资源。

组件库的成果最终要在使用中判断：不同页面能否稳定采用，设计与代码能否相互对应，修复能否传递到实际产品，业务变化时是否仍容易调整。一个长期无人更新、使用时总要绕开的“大而全”组件库，很难减少团队的工作。

从平台控件、网页工具包到企业设计体系，反复出现的需求是相通的：让已经解决的问题能够被可靠地再次使用。UI 设计在这里承担的工作，也从完成单个界面，延伸到决定哪些规则值得共享，以及怎样让这些规则在产品变化中继续成立。
