理解大模型 API：服务链路、计费与选择

发布于 2026.10.10AI 辅助：GPT

关键词：大模型 API　·　模型聚合　·　Token 计费　·　提示词缓存　·　服务选型

第一次打开大模型服务平台，容易被一张模型卡片上的信息弄得困惑：输入价格、输出价格、缓存、倍率、渠道、TPM、最大 Tokens。这些词都和调用模型有关，却分别描述了不同的事情。

其中一些决定费用，一些控制生成过程，还有一些表示服务容量。如果把它们放在一起比较，就容易出现误判：把“最大 Tokens”理解成吞吐量，把“温度”理解成速度，或者看到“兼容 OpenAI”便认为服务来自 OpenAI。

理解这些信息，可以从一次请求开始。

假设有人把一份报告交给 AI，要求它提炼观点。软件把报告和要求发送出去，某个服务端运行模型，再把生成结果返回。围绕这次调用，需要回答四个问题：请求交给了谁，模型处理了多少内容，结果如何返回，以及最后怎样收费。

沿着这条链路，模型卡片上的术语便有了各自的位置。

模型名称与服务来源

一个平台列出了某个模型，首先说明它提供了相应的调用入口。模型由谁研发、实际由谁运行、用户向谁付费，则需要分别理解。

角色 主要工作 用户购买或使用的是什么
模型研发厂商，通常称为“模型原厂” 研发、发布模型，并可能提供自家 API 原厂提供的模型调用服务
推理服务商 部署模型，利用计算资源处理请求 托管模型的推理服务
云厂商 提供基础设施、部署、模型接入及配套服务 云平台提供的模型服务
模型聚合平台 接入多个模型或供应来源，统一接口、账单及渠道选择 经平台组织和交付的调用服务

这些角色可以重叠。云厂商可以聚合多个模型，模型原厂也可以经营推理平台，聚合平台则可能自行部署部分开放权重模型。

所谓推理，是已经训练好的模型根据输入生成结果的过程。训练负责形成模型能力，推理负责在使用时执行这些能力。一次日常问答，通常属于推理。

对于允许部署且符合许可条件的开放权重模型，不同服务商可以使用自己的硬件运行它。对于其他模型，平台可能通过原厂或其他上游服务获得调用能力。因此，同一个模型名称背后，可能存在不同的交付链路：

使用者 → 模型原厂 API
使用者 → 云平台 → 模型服务
使用者 → 聚合平台 → 上游供应商 → 模型服务

某些平台把推理供应商称为“词元工厂”。这个名称可以帮助理解其经营重点：利用算力持续处理请求，以 tokens 作为计量单位。它并不是提前生产一批文字，再把这些文字卖给用户。具体分类仍要看平台自己的定义。

这也解释了为什么模型名称相同，价格和服务表现仍可能不同。采购条件、运行配置、资源利用率、排队策略和中间服务环节，都可能参与其中。

还有一个经常被混用的词是“官方”。平台自己的官方服务、模型原厂服务、获得原厂合作授权的服务，是不同的描述。 如果平台强调合作或授权关系，应当能提供对应的公开说明。仅有模型名称和品牌标识，还不足以建立这种关系。

API 是入口，Token 是计量单位

API，即 Application Programming Interface，可以理解为软件之间约定好的调用接口。

人通过聊天窗口提出问题，程序则通过 API 发送请求。请求一般包括使用哪个模型、输入内容和生成参数；服务端处理后，返回结果以及相应的用量信息。

接入时，经常会看到三个配置：

配置 作用
Base URL 告诉软件把请求发往哪个服务地址
API Key 调用凭证，用于识别账户、权限及相应额度
Model ID 指定要调用的模型；某些平台还会在其中附加渠道标记

API Key 有时也被称为“令牌”，英文同样可能写作 token。但它与计费中的 token 含义不同：前者是凭证，后者是模型处理内容的计量单位。

文本进入模型之前，会经过分词处理。一个单词可能对应一个或多个 tokens，一个汉字也不能固定等同于一个 token；不同模型的分词方式可能不同。图片、音频和视频还可能采用各自的计量规则。Google 的 Token 说明

价格表里的单位通常是：

  • K：一千，即 1,000。
  • M：一百万，即 1,000,000。

因此，0.02 元/K tokens，等于 20 元/M tokens。只有先统一单位，价格比较才有意义。

调用中的输入 tokens，也不只是这一次手动输入的问题。请求携带的系统指令、历史对话、参考资料和工具描述，都可能占用输入。一个看似很短的追问，背后可能再次携带一份长报告。

输出 tokens则对应模型生成的内容。对于具有推理能力的模型，还需要核对思考或推理 tokens 的计费方式。屏幕上可见的回答长度，不一定等于全部计费生成量。

聊天产品的会员订阅与 API 额度也应分别理解。前者购买的是某个产品中的使用权益，后者按照接口的规则结算；除非服务商明确说明，两者不能直接互换。

一张价目表，怎样变成实际账单

比较模型价格，最基本的计算是：

调用费用＝各类计费用量 × 对应单价，再加上适用的其他费用。

对于没有缓存和额外项目的简单文本调用，可以先写成：

费用＝输入 tokens ÷ 1,000,000 × 输入单价
＋输出 tokens ÷ 1,000,000 × 输出单价

假设两个平台提供某项服务，报价如下。这里的价格仅用于演示。

每百万 tokens 平台 A 平台 B
普通输入 20 元 12 元
输出 100 元 60 元

当输入为一百万 tokens、输出为二十万 tokens 时：

  • 平台 A：20＋0.2×100＝40 元。
  • 平台 B：12＋0.2×60＝24 元。

在这组相同用量下，B 的费用比 A 低 40%。

这个例子还说明，输出可能占据很大一部分费用。让模型读取长资料后给出简短结论，与让它连续生成长文，成本结构会不同。比较价格时，需要带入自己的输入、输出比例。

如果平台使用积分结算，还要再做一层换算。

假设花 35 元购买 1,000 积分，输入价格为 420 积分/M，那么实际人民币单价为：

420 × 35 ÷ 1,000＝14.70 元/M

不能因为“420”比另一家的“20”大，就认为前者更贵。两者的单位不同。

倍率也需要放回平台的结算规则中理解。它可能表示模型价格相对某个基准的系数，也可能表示输出相对输入的收费比例。若页面已经展示最终人民币价格，再把倍率乘上去，便可能重复计算。

最可靠的核对方式，是选取一条调用明细，把用量、展示单价、扣除额度和充值成本对应起来。价格表负责说明规则，账单负责检验规则怎样实际执行。

缓存为什么能降低费用

反复分析同一份报告时，很多请求的开头是相同的：相同的指令、相同的资料，只是后面的问题发生变化。

提示词缓存，Prompt Caching，允许服务复用符合条件的上下文计算结果。 模型仍然需要根据新问题生成答案；缓存没有把上一次回答直接复制回来。OpenAI 的缓存说明

相关价目表通常会区分：

  • 普通输入：没有通过缓存复用的输入部分。
  • 缓存创建或写入：建立可供后续请求复用的缓存。
  • 缓存读取或命中：后续请求成功复用已有缓存。

缓存还可能有有效期，通常称为 TTL，Time to Live。某些服务提供较短和较长的保留档位，写入价格也随之变化。例如，Claude 的文档区分了五分钟与一小时缓存。这里的一小时指缓存保留期限，并非一小时无限调用。Claude 的缓存规则

“缓存便宜 90%”和“缓存命中率 90%”，则是两种完全不同的描述。

沿用一个假设价格：普通输入为 20 元/M，缓存读取为 2 元/M。

缓存读取单价确实比普通输入低 90%。但如果一百万输入 tokens 中只有 90% 命中缓存，读取部分的合计费用是：

0.9×2＋0.1×20＝3.8 元

相对于全部按普通输入收费的 20 元，下降幅度为 81%。

如果再生成二十万输出 tokens，输出价为 100 元/M，则本次费用为：

3.8＋0.2×100＝23.8 元

与无缓存时的 40 元相比，整次调用下降 40.5%。这项计算尚未纳入缓存创建等费用。

所以，缓存读取单价的折扣、输入命中比例、整张账单的降幅，必须分别计算。

缓存效果还与使用方式有关。大量请求重复稳定资料时，复用空间较大；每次都处理全新内容，则未必有明显收益。提示词的排列、模型、有效期及服务端匹配规则，也会影响是否命中。核对账单时，应查看实际缓存用量，而非仅依靠宣传中的命中率。

容量、速度与生成参数

“能处理很多请求”和“一个回答生成得很快”，描述的是不同能力。

指标 含义 主要回答的问题
TPM Tokens Per Minute，每分钟 token 限额或容量 一分钟内能承接多少计量内容？
RPM Requests Per Minute，每分钟请求限额 一分钟内允许调用多少次？
并发数 同时进行的请求数量 能同时处理多少个任务？
TTFT Time to First Token，首个 token 返回时间 提交后多久开始看到生成内容？
生成速度 通常以 tokens/s 表示 开始生成后，每秒返回多少 tokens？

服务还可能分别限制输入与输出，例如 ITPM 和 OTPM。账户层级、模型以及组织范围，都可能影响实际限额。Claude 的限流说明

如果某项服务标注“TPM 5000W”，其中 W 按“万”理解，那么它表达的是每分钟五千万 tokens 的容量或限额声明。

假设一次请求计入限额的用量为一万 tokens，单从 token 预算计算，这相当于每分钟五千次请求。但实际请求还会受到 RPM、并发和处理能力约束，而且需要确认该容量是账户独享还是平台共享。

对一个偶尔分析报告的人而言，首个结果的等待时间可能更重要；对批量处理大量任务的团队而言，持续吞吐能力更重要。

生成参数则属于另一组概念：

参数或规格 含义
上下文窗口，Context Window 模型一次处理可容纳内容的范围，具体输入、输出约束依模型而定
最大输出或生成 Tokens 本次生成的上限或预算，部分接口包含推理 tokens
温度，Temperature 在支持该参数的模型中，调节采样随机性
推理强度，Reasoning Effort 在支持该能力的模型中，调节推理投入

例如，最大生成量设为 32,768，表示这一次请求的生成预算，不是 TPM，也不代表模型一定会生成这么多。OpenAI 的 max_completion_tokens 明确包含可见输出及推理 tokens。OpenAI 参数文档

温度较高通常使输出变化更大，较低则使选择更集中。它不是速度倍率，也不是正确率开关。降低温度不能保证事实正确，所有模型也并非都支持自由调整温度。

流式输出，Streaming，则是逐步返回生成内容。用户可以更早看到回答，但这与完整任务何时完成仍需分别观察。

聚合平台与网关提供了什么价值

原厂已经提供 API，为什么还会出现聚合平台？

当用户同时使用多个模型时，需要管理多个账户、接口、密钥和账单。不同服务还可能有不同的请求格式及可用性。聚合平台把这些工作集中到一个入口，也可能通过采购条件或资源组织方式提供价格优势。

它的商业价值由此产生：统一接入、统一结算、渠道管理、支持服务，以及采购与销售之间的差价。至于某家平台的低价具体来自哪一项，需要证据，不能仅由折扣倒推出经营方式。

OpenAI 兼容接口体现的是统一接入的一种方式。平台采用相近的请求格式，让已有软件更容易连接。例如，Google 提供通过 OpenAI 库调用 Gemini 的兼容入口；请求仍然由 Gemini 服务处理。Google 的兼容接口说明

这种兼容性首先解决“怎样发送请求”，具体的图片、工具调用、结构化输出及推理参数支持，仍需逐项核对。

其中，工具调用，Tool Calling，通常是模型生成调用某项工具的意图和参数，再由程序或服务执行工具。它不仅要求模型具备相应能力，也要求客户端和接口正确处理完整流程。

另一个相关概念是模型网关，Model Gateway。网关负责把请求转发到配置好的服务，也可能提供协议转换、日志、预算管理和路由。LiteLLM 就提供统一调用及多部署管理能力。LiteLLM 网关文档

网关可以运行在自己的电脑上。此时，“本地”描述的是网关的位置；只要它转发到外部 API，模型计算和请求内容的传输仍然发生在外部。

聚合平台与网关可以同时存在：

应用软件 → 本地网关 → 聚合平台或原厂 API → 模型服务

还需要理解两项机制：

路由，Routing，是按照规则选择模型或供应渠道。规则可能侧重费用、延迟、可用容量或负载。

故障切换，Fallback 或 Failover，是在某个来源失败后尝试备用来源。LiteLLM 的路由文档列出了成本、延迟及限流感知等策略。LiteLLM 路由说明

切换提高了继续完成任务的机会，同时也可能改变实际单价、等待时间和缓存命中情况。不能假设多个来源天然共用同一份缓存。重试产生的费用，也要以平台账单规则为准。

因此，自动路由服务的报价，应当与实际选择的渠道一起核对。模型卡片上最便宜的渠道，不一定是每次请求最后使用的渠道。

怎样判断实际性价比

价格比较最终要落到一个结果：任务是否完成，结果是否达到要求。

对于摘要任务，可以检查关键观点是否遗漏；对于信息抽取，可以检查字段是否完整、能否追溯原文；对于代码任务，可以检查实际运行和必要测试。不同任务需要不同标准，否则“回答看起来不错”很难形成可靠比较。

下面再用一组假设结果说明：

同样的 100 个任务 服务 A 服务 B
API 总费用 15 元 10 元
达到预设验收标准的结果 95 个 50 个
每个合格结果的 API 成本 约 0.158 元 0.20 元

B 的账单更低，但按这批任务的合格结果计算，A 的成本更低。若再计入重试、人工修订和等待时间，差异还可能变化。

反过来，如果两项服务在自己的任务中结果接近，低价服务当然可能更值得选择。关键是用同一组任务、相近配置和清楚的验收标准建立依据，而不是凭品牌或两次回答的措辞作判断。

可以保留一个小规模任务集，先检查以下信息：

核对项目 应取得的信息
服务来源 实际模型版本、部署或转接方式、必要的合作说明
结算规则 输入、输出、缓存及其他项目的实际单价；积分与倍率如何换算
功能支持 自己需要的图片、工具、结构化输出及生成参数是否有效
性能表现 首个结果等待时间、完整耗时、失败及中断情况
路由与账单 实际渠道、切换条件、重试费用以及可查询的用量明细
使用条款 余额有效期、退款条件、数据处理范围及服务保障

对初次使用 API 的人，一条可以核对清楚的真实调用记录，往往比更多模型卡片更有帮助。它把请求、模型、渠道、tokens 和扣费连在一起，让抽象术语成为可检查的事实。

当这些信息能够对应起来，“哪个平台更划算”才有了明确的比较对象：在自己的使用方式和验收要求下，哪个服务能以可接受的成本，持续交付所需结果。
