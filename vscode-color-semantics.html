VS Code 工作台的色彩语义：从文件识别到变更审阅

发布于 2026.11.22AI 辅助：GPT

关键词：VS Code　·　色彩语义　·　UI 视觉　·　交互设计　·　可访问性

This article is available in Chinese.

研究问题与分析思路

VS Code 把哪些信息交给颜色表达？用户看到一个颜色时，怎样知道它在当前区域代表什么，并据此决定下一步做什么？ 这个问题来自文件树里一个容易忽略的细节：同一行中，文件图标、文件名和行末字母可以各有颜色。

先观察同一份文件。 比较一个 TypeScript 文件在打开、修改保存和出现报错时的样子。左侧图标、文件名文字、右侧标记，哪些保持原样，哪些跟着操作改变？当报错和未提交修改同时存在，一行里还读得出几件事？观察时记下颜色主题、文件图标主题与语言支持，再判断哪些现象能在另一套配置下复现。

再沿一次任务追问颜色的价值。 以“已取消订单混入待处理列表”为例，从找文件、读筛选条件、定位错误，一直看到审阅修改。每到一处都问三个问题：用户此刻要判断什么？颜色让他先发现了什么？还得看哪段文字、哪个符号或哪份对照才能确认？例如，文件名可以提示哪里有修改，具体改了哪条规则，要打开差异才能读出来。

最后把局部放回工作台。 对照编辑器的语法着色、搜索命中、诊断波浪线、版本差异，以及选中和键盘焦点。尤其留意两种红色：表达式下的红线和差异视图中的红色行底，分别让用户去读错误原因和旧版内容。它们怎样借位置、形状、面积和旁边的文字交代各自的含义？

从 UI 与 UX 两侧检验。 UI 上看颜色画在哪里、占多大面积、与底色有多强的对比。UX 上看读者能否借此找到对象、确定操作位置、解释改动。再看一次高对比度主题：当整行填色变成轮廓，还有哪些线索能让人准确说出哪一行被删除、哪一行被加入？

读图前，先看一条订单为什么出现在这里

假设你在验收订单页。点开“待处理”，看到两笔订单：A 等待处理，B 已经取消。标签上的三个字写对了，卡片上的状态也写对了，列表却多出了一笔。你给开发者的验收条件可以非常具体：拿 A（待处理）、B（已取消）、C（已支付）三笔订单试一次，进入列表的应该只有 A。

开发者接手时还不知道问题在哪份文件里。这个例子中，labels.json 保存界面文字，filter.ts 写着决定哪些订单进入列表的规则。两处都可能搜到 pending（待处理）。搜索把可能有关的地方点亮；阅读命中前后的内容，才能分清哪处负责“叫什么”、哪处负责“让谁进来”。这也是写代码时一次很平常的往返：读过一个命中，发现它只管文案，就回到结果列表选下一处。

找到规则后，开发者会编辑并保存文件，读编辑器指出的问题，用几笔已知状态的订单检验行为，再核对准备交付的修改。下文七张图按观察需要取景：图 1、2 展示文件已有改动时的样子；图 3 展示怎样找候选位置；图 4、5 特意引入一次拼写错误；图 6、7 对照修复前后的规则。读每张图时，可以问：开发者刚才还不知道什么？看过这个颜色之后，他能决定去哪一步？到了那里，还要读什么才能作决定？

先看文件树里的两行。labels.json 左侧有一对黄色花括号，文件名接近白色。再往下，view.json 左侧也是黄色花括号，名字却是绿色，行末还多了一个绿色的 U。如果黄色代表 JSON，绿色又代表什么？为什么同一个文件需要两种颜色？

图 1　资源管理器局部。先纵向对照两个花括号，再横向看绿色文件名和行末的 U。本文配图实拍自 macOS 上的 VS Code 1.147.0，使用 Seti 文件图标主题和本地 Git 示例项目。图 1 至图 6 采用 Dark Modern 配色，图 7 切换为高对比度主题。点击图片可看原尺寸。

答案可以从一个小实验中得到。两份文件都是 JSON，所以左侧的图标相同。Git 是记录项目版本历史的工具，VS Code 的“源代码管理”面板能查看它记录的变化。把已有的配置文件复制出一份，Git 会把尚未跟踪的新文件列为 untracked。图中的绿色名字和 U 表达的就是这层关系。用户即使完全看不出绿与白的区别，也能沿着文件名读到 U，再去源代码管理里核对这份新文件。只记住“JSON 是黄色的”，会漏读后半条信息。只记住“绿色代表新增”，又可能把尚未跟踪误读为已经加入下一次提交。

一、文件树的一行容得下几件事

从左到右读图 1。文件图标位于每行相同的位置，面积很小。连续扫几行时，蓝色 TS、黄色花括号和说明文档图标能粗略分开实现、配置与文字材料。对不熟悉项目的人，这是一种廉价的初筛：当目标是修改筛选计算，先读 TypeScript 文件比逐一打开所有配置更有根据。但是，目录中若有二十个同类型文件，二十个蓝色 TS 就几乎没有区分力。下一步得读文件名、上级目录，必要时搜索符号。颜色节省的是识别材料种类的那一下，并没有解决“业务规则究竟写在哪”的问题。

图标和文件类型的关系也有边界。图标主题可以按完整文件名、扩展名或语言标识匹配图标。两份扩展名相同的文件有机会显示不同图标，例如某个工具的专用配置文件可以获得单独的图形。用户也可以更换文件图标主题。真正能迁移到另一个项目的经验是“到名称左侧找辨认文件的线索”，至于具体图形和颜色，要结合当前主题学习。VS Code 文件图标主题说明

现在横向读 filter.ts。左侧仍是蓝色 TS，文件名偏黄褐色，右端有 M。它是一个已经纳入版本管理、本地做过修改的文件。仅修改内容，文件的身份没有变；与仓库中已有版本的关系变了。这解释了为什么同一行需要两套信号。图标处回答“我打开它大概会看到什么材料”，名字和行末装饰回答“当前工作是否动到了它”。对前一问题，标记稳定有利于熟悉项目。对后一问题，标记恰恰应当在特定操作之后变化。

这里还有一个版式选择。文件名是用户找对象时本来就会看的位置，直接改变前景色，余光也能发现哪几行值得看；M 和 U 排在右侧，适合在已经停下来的那一行上精读。如果仅保留颜色，初次使用者很难从黄褐色推断出“已修改”。如果只剩字母，目录较宽、文件很多时，目光需要频繁从名字移到右侧。这两个编码覆盖了不同距离上的阅读。文件名仍然完整，用户可以先快扫，再放慢读出具体状态。VS Code 的 Git 资源颜色定义

回到开头那两份 JSON。假设马上要提交订单修复，绿色的 view.json 会让人注意到工作区里还有一份新文件。仅凭颜色，无法判断它是复现故障用的临时配置，还是产品应该随修复交付的新默认值。需要打开内容、看它由谁引用，再决定是否暂存。发现一项需要判断的变化，是文件树在这里完成的工作。把“决定是否纳入版本”的动作留给能展示内容和暂存分组的地方，可以避免一次扫视替代一次审阅。

二、走进编辑器，颜色开始解释一句代码的结构

图 2　同一工作区的编辑器局部。左侧第 4 行附近有一条窄蓝标记；文字内部，函数名、关键字和引号内的状态值各有着色。两处颜色作用于不同范围。

把第 4 行单独读出来，return orders.filter(order => order.status === 'pending');。眼睛要从这一串字符中找出三件事：从哪里开始筛选、拿什么字段比较、允许什么值通过。深色背景上，filter 和引号内的 'pending' 有不同的前景色。读者可以先定位一个像调用的片段和一个字符串，再顺着中间的运算符读成完整条件。把整行换成单色，括号、引号、点号和空格都还在，含义仍可解出，只是初次定位的工作更多落在逐字符辨认上。

VS Code 的语法高亮会依据语言语法划分文本，再由主题给不同类别着色。启用相应语言服务与主题支持后，语义高亮还可以结合程序分析，进一步区分符号的角色，例如某个名字在这里指向类型、参数还是其他实体。对于未安装对应语言支持的文件，界面能作出的区分会少一些。上图可直接观察到的是不同片段有不同颜色；要精确追溯某个词为何呈现这一色值，可以用 VS Code 的令牌检查命令查看该处匹配的规则。仅凭一张截图很难断定某种颜色由哪一层提供。语法高亮 · 语义高亮

这套着色有一个值得 UI 设计者注意的节制。'paid' 和 'pending' 在同一语法位置都可以是字符串，因此同一主题可以把两者画成相近的暖色。订单业务却把它们当成完全不同的状态。编辑器知道这里写的是一段文字，用户才知道“已支付”和“待处理”能否互换。如果把编辑器的暖色理解成业务上的警告，就会在每行常量里都看到假警报。适合长时间阅读的基础着色，应当能反复出现而无需引发反应。只有出现需要处理的新情况时，界面才需要再加一种更显眼的信号。

图 2 中第 4 行左侧的蓝色窄标记正提供了另一种读法。开启 Git 变更标识时，行旁沟槽可以用标记提示哪些地方相对比较基线发生了增删改。它从文字流中退到边缘，用户读函数时可以略过，需要寻找自己刚改的地方时又可以沿边缘向下找。一个蓝色单词和一条蓝色竖线相隔不过几个字符，用户通常不会把两者混在一起，因为前者有明确的词界，后者沿着行排列。界面借用了文字与页边之间原本就存在的空间区别。源代码管理中的编辑器变更标记

三、搜索高亮给代码加上一层临时的读法

图 3　全局搜索 pending 的实际结果。左侧有 4 个文件、6 处命中；右侧函数名 pendingOrders 只有前半段获得了与查询对应的底色。

项目中同时有状态定义、执行筛选的函数、界面文案和说明文档。一个不熟悉代码的人很可能先搜 pending。图 3 左侧的数字给出了查询范围，命中的字符获得一小段暖褐色背景。右边同一个词在三种位置出现：类型允许值里的字符串、函数名的一部分、实际筛选条件中的字符串。第一次扫视时，这三处看起来都和故障有关。停下来阅读，才会发现只有最后一处直接决定哪些订单能进入列表。

可以专门看 pendingOrders。语法着色把它作为一个完整名称来呈现。搜索只关心查询与原文重合的字符，所以底色在中间截断，后面的 Orders 留在背景上。一个完整的语法单位，上面叠了一段更短的搜索结果。 倘若搜索改为把命中字符统一刷成另一种前景色，底下原有的词类颜色就会部分消失。用局部底色叠加，源文本的结构和临时查询的范围得以同时保留。观察同一词上前景色与底色的边界，就能读出这两种不同的范围。

全局搜索侧栏和编辑器内的查找也有不同的空间任务。在侧栏，按文件分组和每组计数可以帮助决定先打开哪份文件；命中文字周围保留的片段可以帮助排除只写了说明的命中。在文档内逐项查找时，还需要知道“按下一项会从哪里继续”。因此编辑器的主题定义分别为当前命中和其他命中提供不同的颜色或边框。前者记录当前位置，后者显示这一词在周围的分布。相邻几行都有同一词时，这个区别尤其有用。VS Code 查找颜色定义

图中的一个小细节能说明“永久属性”与“当前操作”的差异。左侧 view.json 仍然带着绿色 U，它的搜索片段里却叠着暖色背景。改变查询，会改变暖色矩形的位置和数量；只要该文件仍未跟踪，U 所表达的关系就没有因此变化。对用户而言，这是两种相互独立的操作后果。能分开读懂它们，就不会把“搜索结果中看不到文件了”误以为“刚才的更改已经消失”。

四、一处拼写错误，怎样从工作区定位到几个字符

图 4　把合法状态 pending 暂时误写为 pendng 后的同一个文件。文件树里出现红色的 1 和 M，编辑器把比较表达式画上波浪线。第 4 行的版本变更标记仍在。

这里的“类型检查”可以从一个下拉选项来理解。产品约定订单状态只有待处理、已取消、已支付三种，示例代码也把这三个可用值声明了出来。编辑器据此能提醒开发者某个值拼错了。至于“待处理列表应允许哪几种状态进入”，则由产品规则决定。

为了观察两种状态怎样共存，暂时删去 pending 里的一个 i。它依然带引号，语法着色仍把 'pendng' 当作字符串。示例把订单的合法状态限定为三个值，TypeScript 因而能发现这个比较与已声明的取值没有交集。红色波浪线横跨一段比较表达式。图中最值得看的是两个边界：暖色文字停在字符串两端，波浪线从被比较的属性附近就开始了。前者描述一个词是什么，后者指出语言服务对整项比较有疑问。问题与哪几个字符有关、需要修改哪一个字符，仍要结合诊断消息和上下文判断。

现在回头看文件树。图 1 中带 M 的文件名偏黄褐色，图 4 中同一文件的名字偏红，右侧可同时看到“1”和“M”。原来“已修改”仍然成立，界面又有了一件更值得提醒的事。一个文件名在同一时刻只能用一种主要前景色，两种状态却都可能影响下一步。数字和字母让两种事实仍有各自的落点。这里记录的是本次主题、设置和扩展组合实际呈现的结果。换一个装饰提供者或关闭某类标记，显示组合也可能变化。

图 5　同一次错误在 Problems 面板中的记录。即使长消息被截短，仍能读到错误图标、TypeScript 诊断编号和行列位置。

如果文件树只有红色文件名，用户到这里仍要从头读文件。波浪线进一步把视线缩到表达式，Problems 面板补上可阅读的说明和可跳转的位置。三处表达的是同一诊断，各自提供不同精度：在目录里决定打开哪个文件，在代码中确定要检查哪个表达式，在列表里知道语言服务为什么提出异议。把完整报错塞进文件树会挤走文件名，只在底部放一段错误文字又会增加回到原处的成本。红色在这条路径上负责引出注意，范围、位置和文字逐步接手解释。VS Code 的错误与警告

这种分工也揭示了诊断对业务判断的边界。这次故意拼错的值能被类型系统发现。原先的故障却是 status !== 'paid'：比较合法，状态也合法，只是纳入了不该出现的订单。表达式完全可能没有红色波浪线。修正拼写后诊断消失，只能说明这一项已知的不一致消除了。如果要判断需求有没有实现，要给函数一笔已取消订单，看它是否真的被排除。从 UI 的角度看，同一条波浪线有清楚的出现条件，也应有同样清楚的消失含义；越过这层含义，用户容易把安静的界面读成对业务的保证。

五、差异视图里的红和绿，必须连同比较基线一起读

图 6　修正拼写后，打开源代码管理里的 filter.ts。真实的内联差异视图把旧行和新行上下排列。注意减号、加号，以及 !== 与 ===、paid 与 pending 两组成对变化。

这次修复有趣的地方，是最小的字符改动决定了最大的业务差异。旧行用 !== 'paid'，只把已支付订单排除；一个已取消的订单仍然符合条件。新行用 === 'pending'，直接指定允许进入列表的状态。看图 6，先把目光放远一点，红、绿两条带状区域让人看出变化集中在一处。靠近读，会看到两个颜色更实的局部。最后还得读符号本身：运算符改变了，比较的值也改变了。大面积的色块指示行，小面积的强调指示行内差异，原有文字让使用者能判断这一改法的后果。

这解释了差异视图为什么可以用整行背景，普通编辑时却适合把改动缩到行边。日常编辑可能持续很久，用户需要看外层函数、参数和上下几行，所有改动都铺满强色会把其他代码挤到次要位置。进入差异视图，任务缩小到“两个版本之间发生了什么”，铺色的范围正好覆盖要比较的对象。即便如此，相同的函数上下文仍应可读。去掉它，人只看到两个状态值的替换，还不能确认这是订单筛选、订单标签，还是报告统计里的变化。VS Code 差异编辑器颜色

这里的红与图 4 的红有本质不同。旧的筛选条件被删去，即使用完全正确的代码替换另一段完全正确的代码，旧行同样可以被标红。诊断的参照物是语言规则、类型信息或检查器的判断；差异的参照物是另一份文本。前者的下一步是读消息、判断是否修复，后者的下一步是对照两侧内容、判断这项修改要不要保留。理解哪两份材料在比较，远比记住“红色意味着坏事”可靠。图 6 的减号、加号和旧新顺序，在颜色较难分辨时仍然保留了比较方向。

第一次读 Git 差异，可以先分清三个动作。保存把编辑器里的改动写进电脑上的文件。暂存是挑出本次准备记录的改动，可以只选其中几行。提交把挑好的内容记成一份可以回看的本地版本。本例里，即使筛选规则和另一份配置都已保存，也可以只选规则进入这次提交。之后把提交推送到远程仓库、把产品部署给用户，还各有相应的步骤。

这里说的“基线”，就是这次对照用的那份内容。基线还会随用户的选择变化。在 Git 面板里打开未暂存修改，可以比较工作区与暂存区；从已暂存修改进入，则通常比较暂存区与最近一次提交。设想先把正确的 === 'pending' 暂存，之后又在编辑器把它误写成 'pendng'。这时同一个文件可以同时出现在未暂存和已暂存两组里。两处都可能看到绿色新增文字，绿色本身无法说明哪一份会随下一次提交送出。需要看入口属于哪组、当前比较哪两个版本，再去审阅相应的行。界面倘若只保留漂亮的红绿对照、去掉分组标题，仍然能让人找出区别，却会让人对交付内容作出错误判断。VS Code 暂存与提交

这一点也适用于左侧的绿色 U。它提醒用户 view.json 还未被跟踪；差异里的绿色行表示相对另一侧增加了内容。这两种绿色都有“多出来”的直观联系，实际指向却相差很大。前者以文件为单位，后者以文本为单位。前者不能说明文件准备好了，后者也不能说明新增逻辑符合需求。这里的设计价值恰好在于，用户可以先利用相近的颜色印象发现变化，再用位置、单位和比较对象把含义收窄。

用三笔订单读完这次改动

把图 6 的两行翻成验收时能直接使用的话。红底旧行说“凡是还没支付的都放进来”，绿底新行说“只把待处理的放进来”。用开头三笔订单实际运行这两个筛选条件，旧规则返回 A、B，新规则只返回 A。A 应当留下，C 始终在列表外，只有 B 能区分这一次的修复有没有生效。若只拿一条待处理订单做测试，新旧两个版本都会通过。

现在就能看出审阅和验证各自回答了什么。红绿差异把人带到发生替换的一行，读运算符和值可以解释“为什么 B 会被排除”；给规则输入样本、查看返回的订单，才能观察“B 是否真的被排除”。如果规则的样本结果正确，实际订单页仍然显示 B，下一步应当查页面调用了哪份规则、传入了什么状态值。此时再提高差异颜色的对比度，已经帮不上这个判断。

六、工作台的底色、选择和焦点也在分配注意力

回看图 3。搜索框周围有一圈蓝色，匹配片段有暖色底，左边资源的 Git 标记仍保留各自的颜色。如果把这些强调一律理解成“当前最重要的东西”，很快会遇到矛盾：到底该看输入框，还是该看匹配词？其实它们分别回答“我继续打字会改哪里”和“我刚输入的词出现在哪里”。在搜索时，目光往往落在要阅读的结果上，双手却仍然留在输入框。视觉关注与键盘输入可以暂时分开，正是工作台要支持的一种姿势。

焦点、选中和激活也值得分开。一个打开的文件可以继续显示在中央；左侧某个结果可以保持选中；与此同时，键盘焦点已经移入搜索框。三件事都可以成立。假如每次光标回到输入框，编辑区就取消当前文件的身份提示，用户要重新辨认自己正在哪份文件旁边搜索。反过来，如果所有已经选过的行都画上和输入焦点一样强的外框，按下方向键前又会很难判断哪个区域会响应。VS Code 允许主题分别定义列表有焦点和失去焦点时的选中样式，也提供焦点边界。视觉的工作是让持续的选择与此刻可操作的位置同时可读。VS Code 列表与树颜色

再看普通主题下的大片深灰。文件名、输入框、代码和面板标题的亮度各不相同。屏幕上面积最大的颜色，承担的往往是最慢变化的关系，比如哪里是侧栏，哪里是可阅读的编辑表面。越稳定的背景，越方便观察其上的小变化。文件名从黄褐变红，波浪线从无到有，查找矩形随着输入缩小，都必须在周围相对安静的情况下才能被认出。把每个文件类型扩成整行彩色背景，确实会让分类抢眼，却会与列表选中底色和搜索命中争夺同一片面积。这种比较能解释图标为什么甘愿只占行首一小块。

底部状态栏采用另一种密度。示例界面左下有分支和问题计数，右下有光标行列、编码和语言模式等短信息。打开普通 TypeScript 文件时，这些项目可以持续可见，供需要时扫一眼；逐项添加强色会迫使用户在每次阅读正文时忽略同一批提醒。在典型调试状态下，主题又可以给整个状态栏分配专门的背景角色，使用户在看不同文件期间仍能辨认当前环境。区别在影响范围：一处类型错误属于某段代码，调试会话则可能跨越多份文件。把前者铺到窗口底边会夸大局部问题，只给后者画一个语法词大小的色块又容易被错过。VS Code 状态栏设计指南 · 状态栏主题颜色

七、换一套主题，检查哪些信息真正经得住变化

图 7　同一文件、同一基线、同一对差异行，将配色切到 VS Code 内置的深色高对比度主题后实拍。与图 6 对照，行内文字和加减位置相同，整行填色的作用更多由轮廓承担。

图 6 和图 7 可以用手指对着读。先定住第 4 行，再找 paid 和 pending。两项内容没有移动，改变的是眼睛如何到达它们。在普通深色主题下，先被发现的往往是横跨一行的着色面积，局部替换再以较深底色浮出来。高对比度主题的黑底上，内容边界、行的范围和小片段轮廓变得突出，字符本身仍然可以被逐字核对。相同的操作，并不要求不同主题呈现一样多的颜色、一样大的色块。它要求读者切换主题后仍能认出哪里有差异、差异从哪里到哪里，以及两侧谁增谁减。

这也给“产品色彩规范”提供了一个实际例子。若规范只写“红色用于错误”，就无法用它描述图 6；若只录入一排颜色值，换主题时又很难知道哪些地方要一起调整。VS Code 的主题系统把用途写进可配置的角色：文件是否修改有自己的角色，当前搜索命中与其他命中分别有角色，差异的整行背景与细粒度文字背景也能分开处理。图标则另有主题机制。产品保留的是这些可区分的关系，具体主题选择用怎样的亮度、边界和色相来承载。对设计者来说，先列出用户必须分辨的两种状态，比先决定要用多少种灰更接近问题。VS Code 颜色主题机制

不过，有了颜色角色并不自动保证看得懂。判断这一点有个简单方法：暂时忽略色相，逐项说出还剩下什么。图 1 的文件名有后缀、左侧有不同图形、右侧有字母。图 4 的错误有波浪线，图 5 还有消息与位置。图 6、图 7 的增删有加减号、顺序和原文。搜索结果也按文件分组并保留匹配上下文。反过来，当命中特别短、背景和正文亮度接近时，即使读者能看见搜索计数，仍可能找不到具体是哪几个字符。可访问性需要分别检查“知道存在几个结果”和“能指出结果在哪里”，这两种成功条件不可互换。W3C 对颜色使用的说明

以这组画面做一次设计评审，可以给阅读者三个问题。第一，只看图 1，指出哪两个文件属于同类、哪一个还未跟踪，并说出依据。第二，只看图 4，指出哪一处是 Git 修改，哪一处是类型检查报错。第三，看图 7，解释旧规则和新规则各允许哪几种订单通过。第一题检查颜色与类型、版本的对应，第二题检查信号共存，第三题检查读者能否从显眼的差异回到业务含义。答错第三题，原因可能是比较运算符不熟悉，也可能是图里恰恰看不清运算符；设计者先区分这两个原因，才知道应该补一个说明，还是增强局部辨识度。这些是可检验的设计推断，文中的截图没有测量用户完成任务的速度。

八、从一行文件回到整个产品

这次排查中，有三种情况特别容易混淆。看到绿色文件名，以为修复已经可以提交；看到暖色命中，以为那段代码就是原因；看到波浪线消失，以为业务已经修好。每一次误读，都把颜色已经提供的线索往前多推了一步。要避免这种误读，界面必须能让人从「发现」继续走到「确认」：从文件名进入版本分组，从搜索片段进入完整函数，从报错位置读到诊断理由，再从行级差异走到真正能验证业务行为的测试。

设计上的取舍因此可以具体到三个尺度。对象的尺度决定颜色画在哪：文件类型靠近图标，词类进入字符，诊断跨到对应表达式，版本差异铺到需要比较的行。时间的尺度决定它何时出现和退去：文件身份可以稳定，查询命中跟随输入，版本装饰依赖 Git 状态，键盘焦点随交互移动。判断的代价决定还要提供什么：粗略找文件可以先靠色块，暂存提交、修复错误和改写规则则需要字母、文字、位置、比较内容支撑下一步。

最后再看开头那行 view.json。黄色花括号缩小了查找范围，绿色文件名让人发现它与同类文件有区别，U 给出了进一步查证的方向。后来，搜索又能在它的一行内容上加一小块暖色，而文件的身份与 Git 状态照旧可读。整套工作台用色最值得借鉴的地方，正在这种小范围的共存里：用户可以用当下最便宜的一瞥发现线索，也始终有机会靠更精确的证据完成下一步判断。
