原文链接：https://lipengfei.top/jotora-technical-choices.html

声笺 Jotora 是一款以语音记录为主要输入方式的个人工具。它的处理流程是：先保存录音，再进行转写，随后根据原文整理内容。

这决定了技术上的先后顺序：**记录必须先可靠保留，AI 处理可以随后完成。**

目前，声笺使用 React Native、Expo 和 TypeScript 开发 Android 应用，本地保存记录，云端调用语音识别和文本整理服务。项目没有自行训练模型，也没有在服务器上部署大模型推理。

## 原始内容怎样保存

手机端使用 SQLite 保存记录信息、原始文本、整理结果和音频地址；原始音频文件保存在应用的私有文件目录中。

两者承担不同任务：

| 内容 | 保存位置 | 用途 |
| --- | --- | --- |
| 记录信息和文本 | 本地 SQLite | 查询、编辑和组织记录 |
| 原始音频 | 应用私有文件目录 | 保留录音，支持回放和重新处理 |
| AI 整理结果 | 与原文分开保存 | 方便阅读，同时保留核对依据 |

原文和整理结果分开，是为了避免模型修改内容后失去事实依据。整理结果有误时，仍然能够查看原始转写或回听录音。

本地保存也有边界：它不能自动等同于异地备份。设备损坏、应用数据被清除等情况，需要单独的备份与恢复安排。

## 云端有两条处理路径

项目中的日用版本和有限邀请版本，使用的入口不同：

| 场景 | 处理路径 |
| --- | --- |
| 日用版本 | 手机 → 火山引擎 API 网关 → veFaaS 函数 → 语音识别与文本模型 |
| 有限邀请版本 | 手机 → 腾讯云轻量服务器 → 后台服务 → 语音识别与文本模型 |

API 网关负责接收请求并转交；函数负责执行调用逻辑。邀请版本中的服务器则运行后台程序，处理邀请授权、用量限制、重复请求识别等事务。

两条路径最终都调用外部模型服务。它们不意味着项目已经具备正式云同步能力：真实记录的正式同步仍未上线，相关方案停留在使用合成数据的技术验证阶段。

## 为什么使用腾讯云轻量服务器

项目于 2026 年 8 月购买了一台腾讯云轻量应用服务器：

- 地域：上海；
- 系统：Ubuntu 24.04；
- 配置：2 核 CPU、2 GB 内存、40 GB SSD；
- 带宽：2 Mbps；
- 月流量包：100 GB；
- 当时实付：**105 元，三个月**。

这台主机最初服务于国内部署与同步方案验证，后续复用于官网和有限邀请服务。

它的主要工作是运行网页和后台接口、转发模型请求，以及保存少量服务状态。模型计算由云端供应商完成，因此没有为它配置 GPU。

服务器使用 Caddy 处理 HTTPS 和反向代理，再把请求交给 Node.js 后台。后台使用 SQLite 保存邀请和调用管理所需的状态；部分处理结果还会短期缓存，不能将其描述为“云端完全不保留内容”。

这套配置适合当前的小规模用途，但没有证明能够支持大量并发。尤其是 2 Mbps 带宽，在音频上传场景中可能形成限制。是否升级，应当由实际上传耗时和服务负载决定。

## 语音转写与文本整理分别用什么模型

### 语音转写

项目使用火山引擎的**录音文件识别 2.0**。

录音完成后，音频上传至临时对象存储，再提交识别任务并获取结果。这是一种录完后处理的方式，与声笺当前的使用流程相符。

临时音频有处理后的删除逻辑，以及一天过期的生命周期规则。生命周期清理是异步过程，因此不能把它写成“所有文件一定在精确的 24 小时内删除”。

### 文本整理

文本整理默认使用 **Doubao-Seed-2.0-lite**，项目记录中的具体模型版本为 `doubao-seed-2-0-lite-260428`。

整理任务主要是修正转写中的明显问题、调整段落，并从原文中识别事实和待办。这类任务对忠实性、响应时间和费用的要求，比复杂推理能力更直接。

项目要求模型根据原文返回结构化内容，再由程序组织展示。这样可以减少不同位置分别生成、相互矛盾的情况。

选择这个模型，依据的是任务范围、可用价格和国内调用条件。项目没有完成覆盖所有候选模型的统一评测，因此不能据此宣称它在准确率或综合能力上优于其他模型。

Gemini 曾作为可选方案保留，但项目记录中出现过目标网络下调用不稳定的情况，因此没有作为当前国内使用的默认方案。

## 一次处理大概多少钱

费用需要分成语音和文本两部分。

项目当时记录的参考价格为：

| 服务 | 参考价格 |
| --- | --- |
| 录音文件识别 2.0 | 约 0.8 元／小时 |
| Doubao-Seed-2.0-lite 文本输入，输入长度不超过 32K 的档位 | 0.6 元／百万 tokens |
| 同档位文本输出 | 3.6 元／百万 tokens |

以上是项目选型期间记录的价格，实际计费应以对应模型、服务档位和账单为准。[火山引擎语音计费说明](https://docs.volcengine.com/docs/DoubaoVoice/Billinginstructions-21?lang=zh)、[方舟模型服务计费说明](https://docs.volcengine.com/docs/ark/model-service-pricing?lang=zh)

举一个明确的假设：

- 音频长度为一分钟；
- 整理请求消耗 2,000 个输入 tokens，包含系统指令和转写文本；
- 返回 500 个输出 tokens。

那么：

**语音转写：**

> 0.8 ÷ 60 ≈ 0.0133 元

**文本整理：**

> 2,000 ÷ 1,000,000 × 0.6  
> ＋ 500 ÷ 1,000,000 × 3.6  
> ＝ 0.003 元

两项合计约 **0.0163 元，即 1.6 分钱**。

这只是说明计算方式，不是实测平均成本。它没有包含网关、函数、对象存储、流量、重试和可能的最低计费单位，也没有扣除赠送额度。

固定支出则另算。目前明确的两笔购买记录是：

- 轻量服务器：105 元／三个月；
- jotora.cn 域名：33 元／一年，注册期限为 2026 年 8 月 25 日至 2027 年 8 月 25 日。

两笔合计 **138 元**，但这不是项目全部累计成本。模型、其他云资源和工具费用，仍需要完整账单才能汇总。

## 为什么没有采用七牛云

当时主要比较了七牛云的计算和存储产品，需要分别看待。

**QVM 是云主机，可以运行后台程序。** 从技术能力上，它能够承载 Node.js 和 SQLite，并不存在“声笺不能使用七牛云”的结论。

但比较价格时，需要把主机、磁盘、公网 IP、带宽和备份等组成放在一起核算。项目当时已经取得腾讯云轻量服务器的完整套餐报价，没有取得能够证明同等条件下更合适的七牛云完整报价，因此选择了当时更明确的方案。[七牛云 QVM 计费说明](https://developer.qiniu.com/qvm/4238/qvm-billing-contrast)

这不足以推导出“七牛云一定更贵”。

**Kodo 是对象存储，主要保存和分发文件。** 它可以用于音频文件或备份，但不能直接代替数据库处理会话、重复请求和事务状态。对象存储与数据库处于不同层次，不能仅凭存储单价相互替换。

Kodo 被保留为潜在的加密备份方案，后续可以与腾讯云 COS 比较容量、请求、取回和传输费用。目前没有把这一候选方案写成已经部署或通过恢复验证的备份能力。

后续邀请服务出现时，腾讯云服务器已经购买并可复用。此时继续使用现有资源，能够避免再增加一套主机和维护工作。这是后续复用的理由，与最初购买时的比较依据有所不同。

## 其他方案为什么暂时没有推进

| 方案 | 已有依据与当前处理 |
| --- | --- |
| Cloudflare Workers、Durable Objects | 合成数据验证曾通过，但目标手机在当时国内网络下访问测试入口失败，没有作为正式国内入口 |
| MySQL | 原开发实例已释放；正式同步需求尚未成立，避免持续保留空闲实例 |
| 更高配置服务器 | 当前缺少实际负载证据，暂不升级 |
| 正式账号和云同步 | 尚未进入日用版本，不作为已经完成的能力 |

这些选择都受到当前规模和使用证据的约束。声笺现阶段更需要确认的是：录音能否可靠留下，转写是否稳定，整理是否忠于原文。新增基础设施，应当解决已经出现的问题。
