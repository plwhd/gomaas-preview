# VS Code 的活动栏：从工作任务推导一级入口

作者：李鹏飞  
发布于：2026-11-22  
AI 辅助：GPT  
关键词：VS Code · 活动栏 · 主侧栏 · 交互设计 · 任务恢复  
原文链接：https://lipengfei.top/vscode-activity-bar-ux.html

“待处理”筛选里混进了已取消的订单。接到这条反馈时，开发者很可能知道界面上的现象，还不知道规则写在哪。有人先翻目录，有人搜索状态值，有人会先看本地是否已经有别的改动。三个动作都发生在同一个项目里，却需要三份不同的索引。目录按文件归属组织信息，搜索按查询匹配组织信息，源代码管理按文件与版本之间的变化组织信息。VS Code 把打开这三份索引的入口放在同一列。

这里需要解释两件事。第一，为什么这几项值得占活动栏里的位置，有些同样重要的功能却留在编辑器、菜单或其他地方。第二，为什么把入口移过去会改变工作的流畅程度。答案要从一个动作究竟在改变什么入手。选“搜索”会改变手边用什么视图找代码，真正点击一条命中才可能打开另一处代码。保存文件要作用到文件本身，切换分支会改变项目所处的版本。视觉上都能画成一个图标，实际作用范围有很大差别。

本文以 VS Code 的常规文件编辑工作台为范围。订单项目和文件名用于示例。哪些区域可以打开、移动或关闭，以微软的文档为准。它们为何适合某种工作方式，是下面要论证的设计判断。

## 一、一项工作会多次改变提问方式

假设订单项目目前开着说明文档。开发者第一件事也许是弄清楚订单模块在哪里。此时项目的文件夹、相邻文件和命名提供线索，从资源管理器展开目录就能顺着结构认识项目。如果找到两份叫 `filter.ts` 的文件，一份在当前订单模块，一份在历史订单模块，目录关系可以帮助区分它们。此时要解决的是“哪个对象归属于这里”，还没有开始修改。

也可以从搜索进入。开发者可能记得一个状态值，但说不出在哪个模块使用。此时逐层展开目录意味着按项目组织者的路径猜位置。搜索允许从记得的文本入手，把散落在界面筛选、请求参数和测试中的匹配聚到一处。接下来要看匹配的上下文，判断哪一处只是显示标签，哪一处真的决定订单是否进入列表。搜到同一个词，只是缩小调查范围。

找到规则之后，开发者还需要看状态定义，在编辑器里改一处条件，然后验证。测试报错时，可能回到搜索，查是谁把已取消的状态别名传进来。看见现象消失以后，还需要打开源代码管理，检查刚才到底改了什么。假如仓库里本来就有一份未完成的界面样式，如果为了提交修复把所有变更一起选上，就会把两个工作混在一起。这个时候问题变成“下一次提交应该包括哪些变化”，目录位置和文本命中都无法代替对差异的阅读。

顺序并不固定。进入不熟悉的仓库可能先靠搜索，接手别人留下的改动可能先开源代码管理，明确知道文件名时可能直接打开它。甚至在修改后看到一处意料之外的差异，又会返回文件树厘清实际目录结构。**一级入口服务的是反复出现的几种判断，而不是一次任务的几道连续工序。** 活动栏把这些判断的入口留在相近的位置，使用者不用先退出手里的代码，再进入一个完整的新流程。

## 二、资源管理器提供项目中的位置

资源管理器（Explorer）首先提供一份按目录组织的项目视图。文件在树里有上下级和相邻对象，展开时逐步露出细节。它适用于知道某个功能的大致归属、需要认识项目结构，或想比较同一目录中几个相关文件的情况。文件夹一旦展开，也能当作持续几分钟的参考。正查订单状态时，开发者可以先定位模块，再依次打开规则、配置和测试文件，仍然看得见这些文件从哪层目录取出来。[VS Code 资源管理器与活动栏](https://code.visualstudio.com/docs/editing/getting-started/userinterface)

为什么这份目录值得单独展开？因为有时路径本身就是判断依据。两个同名文件打开后，标签可以补充路径，但单看两个标题仍然很难知道哪一个归在历史模块。树里的父目录、兄弟节点和文件相邻关系能立刻提供另外几条线索。若树被做成一次性的文件选择弹窗，选中后当然也能打开内容，但后续确认另一个文件归属时，就需要重新叫出选择器或在两个标签里猜路径。把树留在侧面，是用少量宽度换取可持续的项目参照。

同一个文件出现在树和编辑标签里，解决的是两种地址。树回答这个文件属于项目哪部分。编辑标签回答它被带进哪个编辑组，与哪几份参考文件暂时摆在一起。关闭标签后，文件依然属于原目录。把标签拖到另一组，改变的是并排关系。文件被移动到另一个目录，则改变了项目结构。这三个行为如果被放进同一份扁平列表，用户要额外推断某个动作是改变工作台，还是改变实际文件。

资源管理器还可以容纳大纲、时间线等相关视图。大纲辅助读当前文件的结构，时间线可以帮助查一个文件的本地记录或 Git 历史，它们的信息范围和整棵树并不完全相同。放在同一容器里的理由，是它们能围绕文件定位与上下文查阅一起工作。单独拆出一个最左图标，虽然可以一步到达，却会增加一项常驻入口，还可能分开使用中紧挨着出现的信息。[微软对视图容器和资源管理器的说明](https://code.visualstudio.com/api/ux-guidelines/overview)

## 三、搜索提供一份可以反复修正的查询结果

搜索（Search）的方法是先确定线索，再沿线索找对象。对于订单故障，一个人可能先查 `cancelled`，发现结果里出现许多界面文案，便把范围缩到应用代码，继续找实际过滤逻辑。随后又加上一个包含路径，查状态定义与测试是否都使用同一枚举。这个过程包括输入条件、调整范围、扫结果、读一处源码、返回结果再看下一处。一次查询的结果在这段时间里充当调查清单。[VS Code 跨文件搜索与范围设置](https://code.visualstudio.com/docs/editing/codebasics#search-across-files)

搜索结果也长得像一棵树。它通常按命中文件归组，文件下展开具体匹配。两个层次和项目树不同。项目树告诉你文件所在的目录，这棵结果树告诉你“在当前查询与范围下，这个文件有这些匹配”。在搜索结果里点击一处命中，编辑器得到文件及相关位置，搜索区继续保留这次调查的条件和其余结果。下一项判断可以直接回清单，省掉的是重新把当前代码与“还有哪些地方需要查”接上。要是只保留了搜索框却每次打开命中就清空结果，路径跳转仍然能用，成组核对的任务就要重做一部分。

文件内查找也很常用，却放在编辑器附近。当前目标已经是 `filter.ts` 时，只需找到这份内容里的一个词。查找结果的范围随着当前文件或选区确定，没有必要另外占一个工作台入口。若知道文件名，可以用快速打开直接选择文件，列表选完就能退开。跨文件搜索不同，一开始未必知道目标是哪一份，还可能要来回查看多个匹配，因此值得有可返回的查询视图。VS Code 也提供搜索编辑器。当结果需要更宽的阅读区、有多行上下文或希望独立留一份结果时，可以把结果转到编辑器。目标、作用范围和需要保留多久，共同决定了这些入口的形态。[VS Code 文件内查找、跨文件搜索与 Search Editor](https://code.visualstudio.com/docs/editing/codebasics)

由此也能看出一个细节。只看到结果为空，用户无法马上断定项目里没有这个状态。也许某个目录被过滤，或用户把范围限定在了错误的文件夹。搜索要保留查询和范围，结果才有解释力。当界面说“没有匹配”，使用者得能看见这是在哪组条件下得出的。活动栏负责快捷进入这套视图，真正让搜索可靠的，是展开以后能看见条件、结果和它们如何对应。

## 四、源代码管理给工作结果一个可审查的范围

源代码管理（Source Control）从版本关系观察项目。它把变更集中起来，让用户检查文件、打开差异、选择暂存与组织提交。打开它时，即使一个文件藏在很深的目录，或者没有命中查询，只要属于相应的 Git 变更范围，就可能出现在列表里。反过来，刚打开的文件或刚找到的匹配，未必有任何变更。这份列表的组织原则是修改状态。[VS Code 源代码管理](https://code.visualstudio.com/docs/sourcecontrol/overview)

在订单例子里，修筛选和改界面样式的文件都可能出现在变更列表。开发者能先看到两类改动都存在，然后读差异，决定本次只提交规则和对应的测试。点击某项可以在编辑器区域打开对应的差异，旁边的变更列表仍然能用来继续查阅。暂存决定哪些已修改的内容列入下一次提交。判断一份改动属于哪个工作范围，需要同时看这次要交付的结果和文件里实际变动的几行。一个文件有两段独立变更时，VS Code 也提供选择部分行进行暂存的方式。[VS Code 暂存与提交](https://code.visualstudio.com/docs/sourcecontrol/staging-commits) · [VS Code 按选区暂存](https://code.visualstudio.com/docs/editing/getting-started/tips-and-tricks)

源代码管理有独立入口的必要性，也可以通过两个看似足够的替代方案来判断。一个方案是在文件树里用颜色或字母标记改过的文件。这个提示有用，人在浏览目录时能知道附近哪份文件动过。但只靠目录标记，要收集散在多个模块的所有变化仍得遍历目录，也难以分开已选择与未选择的提交内容。另一个方案是在当前文件旁放一个提交按钮。按钮点起来很快，但当一次修复涉及多个文件时，作用范围可能难以预判。集中变更视图让用户先形成对改动集合的认识，再做会改变 Git 状态的操作。

打开变更视图、选中一处差异、暂存一段内容，依次是三个层级。第一个改变正在查看的视图，第二个定位到一个可核对的对象，第三个改变将要提交的内容。把它们分开，使用者才能先低成本地查看，然后有意识地执行。活动栏入口本身适合经常点，因为选择这种参照通常不会直接提交任何东西。真正有后果的操作，应在已经显示仓库、文件或选区范围的地方执行。

## 五、活动栏选择视图，主侧栏让视图可以持续工作

微软的扩展设计指南把活动栏条目定义为视图容器的入口。一个容器可以包含多个相关视图。点击活动栏中的资源管理器，主侧栏可以展示文件夹、大纲和时间线等内容。点选本身所做的事，是把一组信息和操作带到手边。许多条目的选择在同一个主要侧栏区域生效，侧栏的接收位置比较稳定。用户只需辨认哪种视图被选中，以及展开后的视图要怎么看。[VS Code 工作台 UX 指南](https://code.visualstudio.com/api/ux-guidelines/overview)

可以把这层关系拆成三个连续的选择。在最外层，用户选择用目录、匹配或变更状态观察项目。到了侧栏，用户选择一份文件、一次匹配或一项变更。在编辑器中，用户可以读到内容或差异，再确定要处理的代码位置。三个选择都可能通过一次点击发生，但范围逐级变小。按活动栏不会自动把某个搜到的文件交给编辑器。侧栏选中一个项目后，编辑区才可能打开相关内容。编辑器组最终决定打开后保留在哪块阅读空间。

这里“可以换工具，同时保留原工作”的含义可以写得更明确。设想用户正在左侧编辑组看 `filter.ts`，右侧编辑组留着 `status.ts`。点活动栏里的搜索，只要求主侧栏从目录变成搜索视图。两份代码仍能留在原组里。等用户点击命中，才触发打开目标位置，这时编辑器内容、焦点甚至预览标签可能按当前设置变化。**保持工作现场的是视图切换和对象打开之间的边界。** 如果一次切换同时让编辑器换文件，用户就难以提前知道会丢掉哪份参照。这个边界比“侧栏与主区分别存在”更能解释为什么这样的布局可以工作。[VS Code 界面和自定义布局](https://code.visualstudio.com/docs/configure/custom-layout)

活动栏上这三个类别有几个共同条件。它们能从不同任务阶段进入，入口之外还需要容纳一组信息和操作，打开后可以影响编辑器里的定位，却不会仅因展开就换掉项目或提交成果。它们共享同一片侧栏空间，所以同时常驻的只是很窄的入口。三组内容不一定时时都要看，仍然容易再次叫出来。把这理解成“一级入口专门放最重要功能”，就会把保存、撤销和运行命令也挤进来。更准确的判断是，这里为几类需要持续使用的项目视图保留了快捷入口。

运行与调试、测试、扩展等条目也帮助检验这个解释。调试能展开变量、调用栈与断点，调试中需要反复查这些状态。测试视图可呈现一组测试及其运行结果，依赖相应的测试支持。扩展视图涉及发现、查看及管理扩展，使用频率未必赶得上文件树，但有自己的对象集合和持续操作。这些条目的工作性质存在差异。把它们放在同一条栏里，是因为用户都可以打开一个独立的视图来做事。使用频率和默认可见性可以讨论，是否存在独立视图、怎样与编辑工作并存，是另外两项判断。[VS Code 调试](https://code.visualstudio.com/docs/debugtest/debugging) · [VS Code 测试](https://code.visualstudio.com/docs/debugtest/testing) · [VS Code 工作台视图](https://code.visualstudio.com/docs/editing/getting-started/userinterface#views)

## 六、理论解释的是找路、判断结果和恢复现场

Don Norman 在认知工程中区分了执行鸿沟和评估鸿沟。用这个案例理解，前者是人知道自己想做什么，却还得找出界面上的动作。后者是做了动作之后，需要看懂系统发生了什么。对“找出已取消订单状态在哪里被引用”来说，一个名字明确的搜索入口减少找路的步骤。点开后能看到查询、搜索范围和结果，才能判断刚才的做法是否适合。两个问题由两层界面承担。活动栏提供易找的入口，主侧栏呈现能解释结果的反馈。在设计审查里，入口好找与结果可解释要分开观察。[Norman，《Cognitive Engineering》](https://ics.uci.edu/~dfredmil/inf233-FQ07/oldpapers/Norman1986ch3.pdf)

这个区分能查出一些仅看截图发现不了的问题。例如源代码管理图标上有数字，使用者知道可能有改动，于是点击进去。假设打开以后只有几个没有分组的文件名，依然无法判断每个文件的变化是否已选入提交。这里的问题发生在评估，不是入口。给图标加文字或调到更明显的位置，仍然补不出用户要看的状态。反过来，如果变更视图内容非常精确，却把入口藏在一个含义模糊的“更多工具”下面，用户找不到它，视图的细节也帮不上忙。设计问题因此能落到可以检查的地方。

分布式认知提供另一个视角。Hollan、Hutchins 和 Kirsh 把人的思考与手边的外部表征一起分析。在这个任务中，开发者同时需要知道文件归属、还没读的命中、代码停在哪，以及哪些变化已经准备提交。如果工作台保存了相应的参照，这些关系可以拿出来确认，不必长期靠人的短时记忆维持。能不能并排看某两份信息，则应从比较的需求出发。只需核对一次的定义可以快速查完再返回。规则与定义逐项对照时，把两者分别留在两个编辑器组，外部界面就承担了更多保留位置的工作。[Hollan、Hutchins 与 Kirsh，分布式认知](https://escholarship.org/uc/item/8sb9s5rm)

任务恢复研究进一步解释了为什么要保留现场。Altmann 和 Trafton 的实验发现，任务中断前后能接触到有关线索，有助于恢复任务。对于工作区，可以据此提出一个具体的检查。开发者改到一个条件中途，去看搜索结果后回来，是否还能看见刚才读到哪里、与哪份配置对照、还有哪些匹配没有看过？只恢复文件名，可能还要重新找条件。同时恢复滚动和邻近参照，恢复线索就更完整。受干扰后的恢复和自愿切换视图并非同一个实验场景，这里的用法是借研究提出设计判断，再通过真实任务验证，无法直接推断这个应用能省几秒。[Altmann 与 Trafton，任务恢复和线索](https://escholarship.org/uc/item/18b4r661)

三种理论都没有给出“一级入口必须在左边”这样的结论。它们给出了更有用的判断：依据意图能定位到功能，做完能检查结果，离开再回来时线索还在。若一个方案把入口放到了右边，这些关系依然可以成立。若方案看起来像 VS Code，但切换工具会清掉原视图的条件、重新加载文件，或者把用户送到错误的位置，说明真正需要的交互并没有随外观一起实现。

## 七、左边分工，底部借高度，中心保留编辑面积

把活动栏和主侧栏放在同一边，使选择及其反馈彼此相邻，也使编辑器的内部空间可以独立伸缩。活动栏一列图标需要的宽度相对固定。目录、查询结果和变更列表则经常出现长名称、树的缩进和计数，宽度不够时需要调整。将两层分开，侧栏可以按内容伸出来，入口的位置仍然比较稳定。先预测哪一片会变，再看那一片具体变成什么，比每次从整块工作台上寻找新工具更省力。

一份文件树或变更列表能利用侧面大部分高度。若把它们长期横在编辑器顶部，长列表要么遮住代码，要么拿走编辑器的阅读高度。放在左边会减少代码行宽，因此在小窗口、长行代码或双编辑组的场景中也有实际代价。可以收起主侧栏，或者将侧栏成组停靠到另一侧。VS Code 允许移动视图容器，也允许把辅助内容挪到另一侧或底部。左右的选择可调，入口和被它切换的视图之间的关系更值得保留。[VS Code 自定义布局](https://code.visualstudio.com/docs/configure/custom-layout)

底部面板的默认位置体现了另一种空间选择。终端命令、路径、日志和错误信息会沿一行展开，因此比较依赖宽度。放到编辑区下方，可以从整块编辑区借高度，即使上面并排两份文件，底部仍能拿到较宽的阅读区。微软的面板指南把需要横向空间的辅助视图作为合适对象，并提到用户经常收起面板。对于需要持续观察许多行日志的工作，侧置、单独打开或暂时最大化也可能更合适。[VS Code 面板设计指南](https://code.visualstudio.com/api/ux-guidelines/panel) · [VS Code 终端编辑器](https://code.visualstudio.com/docs/terminal/basics#terminal-editors)

比如刚修完订单条件，开发者只想复跑一次检查。终端在下方出现，上面规则和配置仍在眼前。若结果能链接到测试失败的具体行，就能从输出指向下一处要看的内容。若调试大量输出时需要保留日志的纵向脉络，短横条反而会频繁滚动，移到侧面常有理由。把底部面板和活动栏同时理解为“重要的工具应该放边上”会漏掉核心差别。这里决定方位的是数据的长宽、与主区是否要同时可见，以及用户调用它的时长。

最下方的状态栏也在边缘，不过在布局中承担环境确认。打开文件或切换工作状态时，使用者可以快速确认分支、问题概况、当前语言模式或缩进。官方指南把工作区级的信息通常放在左侧，把较局部的、与当前内容有关的信息放在右侧。状态项可以引出操作，但自身只需要很少的面积。它适合保留在视线可以迅速掠过的地方。一个长差异、一次运行输出或一组测试结果需要可展开的工作区，几枚短状态标记只能给出入口或概况。[VS Code 状态栏设计指南](https://code.visualstudio.com/api/ux-guidelines/status-bar)

## 八、同样重要的功能，为什么不用同一种入口

**一次执行就结束的命令，可以用命令入口。** 保存当前文件、格式化文档、跳到某一行，通常已经有明确对象，只需要发起一次动作。保存很常用，但专门开一整个侧栏来“进入保存”会多出一个空的工作区域。更合适的位置可以是快捷键、命令面板或紧贴编辑器的工具栏。VS Code 的设计指南建议，能由一条命令完成的行为避免搬进侧栏。命令面板与活动栏的分工也由此清楚。命令面板为可能很多的动作提供查找入口，活动栏让少数可持续工作的视图有固定位置。[VS Code 侧栏指南](https://code.visualstudio.com/api/ux-guidelines/sidebars) · [VS Code 命令面板指南](https://code.visualstudio.com/api/ux-guidelines/command-palette)

**作用于当前对象的局部工具，放在对象附近。** 文件内查找从当前文件出发，差异编辑器的上一处和下一处变化也与当前差异有关。把它们放到编辑器附近，用户可以从工具的位置判断它作用于哪份内容。若有两组编辑器，又把当前文件的动作统一挂在最外层图标上，就必须另做非常清楚的焦点与作用范围提示。否则点击前需要猜它会作用到左边、右边，还是整个项目。

**同一对象的不同内容面，适合保留对象身份后切换。** 比如从文本视图换到该文件的预览，变化的是如何看眼前这份内容。比较两个呈现方式时，文件身份需要一直能看见。这个问题与“要不要打开一套项目级视图”不同。只要画出几个图标看起来可以并列，就把“内容面切换”和“跨项目查找”放到同一栏，用户会失去位置对于作用范围的提示。若几个视图都依赖一个明确的选中对象，可以先让用户确定这个对象，再在附近提供相关视图。

**会改变后续操作规则的模式，需要让作用边界一直看得见。** 暂时用搜索视图，和进入一个会让同一次点击产生另一种结果的编辑模式，是不同的决策。判断某个模式是否应当占全局位置，可以问三个具体问题。哪些区域会跟着变？哪些输入的含义会变？用户离开后原来的对象和工作状态怎样恢复？如果影响整块工作区，模式名称与退出方式适合出现在各区域都能看到的位置。若只有当前对象的编辑方式变化，则应把提示贴近这个对象。位置应该由被改变的范围推出。若只是把工具移到旁边，从按钮名称和结果就应读成“展开工具”。若切换会重解释之后的操作，就要清楚表达当前模式以及它会影响哪里。

还有一种容易混入活动栏的内容，是单一工作区范围的信息，例如分支名、运行中或连接状态。若用户主要需要快速确认，短状态标记更节约时间。若点进之后有持续工作，例如处理多条失败、逐项比较文件或管理一组独立对象，才需要进一步判断是给一个独立视图，还是把它并入已经存在的容器。要从“打开以后用户要做什么”判断，而不是按照功能名称的数量分配图标。

## 九、把依据写进布局方案，再用原型验证

开始做一个工作台时，可以从一个包含判断和失败分支的典型任务出发。仍用订单筛选。先记录用户如何知道该查哪里，如何从多条匹配中找到真正的规则，怎样确定提交的范围，以及失败以后要回到哪个位置。比例和栏位还不急着画。先把实际出现的动作分开。查找是得知某事，编辑是改变某处，运行是取得反馈，审阅是决定哪些变化可以进入一次提交。这样划分，保留下来的几组功能分别承担了不同的工作。

接着给每个候选入口写一句可以被证实的定义。例如“提供项目目录及其相关上下文”“保留一次跨文件调查的条件与结果”“列出一个仓库中待核查的变更”。能这样写清，接下来可以比较这组内容是否跨多个文件、是否要多次重访、是否常要与主内容同时可见。如果一个功能写成“把当前文件格式化一次”，它通常已经可以落到具体命令。如果写成“切到另一种操作方式，接下来的点选与输入随之改变”，就要另外明确模式状态、作用区和回程。这样的定义足以把若干看起来都能放在一级入口的想法提前分开。

然后写清楚切换会造成的变化。读着规则文件时打开搜索，查询应出现在确定的区域，原编辑组继续可用。点击命中后，界面需要知道要把目标打开到哪一组，或者提供一种能保留原参照的打开方式。到源代码管理看差异时，列表应让用户辨认所看的仓库和变更状态。看错结果再返回时，已有查询、原文件位置和选中的变更最好可以按需要重新找到。切换的定义比栏位顺序更具体，可以直接变成原型的交互条件。

要比较两个布局，可以让它们承载相同的任务与信息，再只改变真正有争议的地方。例如一版把跨文件搜索放在能收起的侧栏，另一版把它作为选中即消失的命令面板。请人从同一条故障描述出发，要读三个匹配，改完后再重新确认一处。观察从第一个到第二个匹配是否得重新输条件，从结果回规则是否丢了原位置。若眼下只是打开一个已知文件，短命令可能更轻。换到多次筛选与对照的任务，持久视图更可能节省恢复参照的工作。两种结论可以同时成立，因为测试的是不同使用条件。

还有一个实用的对照。让用户先看到项目里有一处自己的旧改动，再完成筛选修复，最后只交付本轮变化。记录他在哪里发现有两组工作，能否看清选入提交的是哪些文件或行。如果误把旧改动一起选上，可以追问是入口难找、变更分组难懂，还是范围状态藏得太深。三类错误分别对应视图入口、内容组织和动作确认。这样得到的反馈能指向可修改的设计，不必重新做几套图标排布来猜原因。

对这个案例，布局方向可以先由工作确定下来。资源管理器、跨文件搜索和源代码管理分别是对同一项目的三种可以持续使用的观察方式。稳定的入口便于切换，紧邻的侧栏承接这些视图，编辑器保留真正被读和被改的对象。当考虑再增加一项功能时，先问用户打开它以后会在里面做到什么程度，离开后还会不会回来，以及这次切换是否改变整块工作区的操作规则。这几个问题回答清楚，才有依据决定它应当占一级入口、留在局部，还是用一次命令完成。
