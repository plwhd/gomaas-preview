# lipengfei.top 的制作：技术方案、上线流程与成本

原文链接：https://lipengfei.top/personal-website-build.html

lipengfei.top 采用静态网站方案：在本地维护文章、模板和代码，生成可以直接访问的网页，再通过 GitHub Pages 发布，使用购买的域名访问。

这套方案没有单独租用服务器，也没有为文章管理配置数据库。当前网站的主要内容是文章和静态页面，筛选、复制 Markdown、下载文章等交互由浏览器完成。

从产品经理的角度看，这次制作主要涉及三件事：确定满足需求的技术结构，建立可靠的发布流程，以及明确建设和维护的成本。

## 网站由哪些部分组成

| 部分 | 实际使用的方案 | 作用 |
| --- | --- | --- |
| 页面结构 | HTML | 定义标题、正文、导航等内容 |
| 页面样式 | CSS | 控制排版、间距和不同屏幕下的显示 |
| 页面交互 | JavaScript | 实现文章筛选、复制和下载等功能 |
| 页面生成 | Eleventy | 将文章、模板和公共数据生成静态页面 |
| 模板 | Nunjucks | 复用导航、页脚和文章结构 |
| 文章内容 | Markdown | 保存便于编辑和转移的正文 |
| 版本管理 | Git、GitHub | 记录修改，保存可追溯的版本 |
| 网站托管 | GitHub Pages | 将生成后的文件提供给访客访问 |
| 访问地址 | lipengfei.top | 使用自定义域名访问网站 |

GitHub Pages 可以直接托管 HTML、CSS 和 JavaScript 等静态文件，并支持自定义域名。这与网站当前的内容形态相符。[GitHub Pages 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

网站使用 Node.js 运行本地构建工具，但访问网站时，不需要启动一个 Node.js 后台服务。访客获取的是已经生成好的页面和资源。

## 为什么后来加入 Eleventy

早期页面直接使用 HTML 维护，页面少时比较直观。随着文章增加，公共内容开始重复：修改一次页脚，需要检查多个页面；新增文章，也要同步维护文章列表、详情页和相关信息。

问题主要出在重复维护。

因此，项目后来引入了静态网站生成器 Eleventy。它把公共页面结构放进模板，把文章标题、摘要、分类等信息集中管理，再生成各个页面。[Eleventy 官方文档](https://www.11ty.dev/docs/)

现在，一篇文章的维护大致分为两部分：

- **文章正文**：主要使用 Markdown。
- **文章信息**：集中记录标题、摘要、分类、关键词和版本等内容。

生成时，再将它们放入统一的文章模板。

这减少了同一信息在多个位置分别修改的情况。旧页面中暂时不适合迁移的部分仍然保留，没有为了统一工具而一次性重写全部页面。

## 域名、托管和 HTTPS 怎样连接

域名和网站托管是两项不同的服务。

**域名**提供访问名称；**托管服务**保存网页文件，并向访客返回这些文件。

lipengfei.top 的注册商是新网，注册时间为 **2026 年 10 月 1 日**，到期时间为 **2031 年 10 月 1 日**，注册期限为五年。

购买域名后，还需要完成两项配置：

1. 在 GitHub Pages 中绑定自定义域名。
2. 在域名解析中，将域名指向 GitHub Pages。

其中，根域名使用 A 记录，`www` 子域名使用 CNAME 记录。DNS 解析的作用，是让浏览器知道这个域名对应的服务地址。[GitHub 自定义域名配置说明](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site)

网站同时启用了 HTTPS。证书由 GitHub Pages 配置和维护，没有另外购买商业证书。[GitHub Pages HTTPS 说明](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https)

## 一篇文章怎样更新到网站

当前流程是：

**维护文章和信息 → 本地生成 → 检查预览 → 发布静态文件 → 检查正式页面。**

本地生成的发布目录，与维护源码和内部文档分开。发布时，只上传需要公开的网页、文章文件和资源。

内部写作说明、未公开笔记、账号配置和凭据，不应因为放在项目目录中就一并上传。

构建过程会先在临时目录中生成和检查结果，通过后再更新发布目录，降低生成失败时影响已有文件的可能。正式发布完成后，还需要核对线上页面，不能只以“本地构建成功”判断发布完成。

文章更新也需要保持几个位置一致：

- 文章详情页；
- 文章列表中的标题、摘要和入口；
- 提供下载的 Markdown 文件；
- 页面显示的文章版本。

版本管理保留了修改记录。如果发布后出现问题，可以根据既有版本恢复，不必凭记忆重新拼回旧稿。

目前能够确认的成本情况如下：

| 项目 | 当前情况 | 成本口径 |
| --- | --- | --- |
| lipengfei.top 域名 | 已注册五年 | 实付金额尚未核实 |
| GitHub Pages 托管 | 使用公开发布仓库 | 当前方案未产生独立托管费用 |
| HTTPS 证书 | 由 Pages 配置和维护 | 未单独购买证书 |
| 独立服务器 | 当前网站未单独租用 | 没有这项新增支出 |
| 文章数据库 | 当前未配置 | 没有这项新增支出 |
| AI 工具 | 使用已有工具辅助制作 | 未单独分摊到网站 |
| 制作与维护时间 | 持续投入 | 尚未记录完整工时 |

域名证书可以证明注册期限，但不能证明付款金额。因此，暂时不能据此计算网站的准确总支出或年均成本。

“没有租服务器”也不代表网站不存在托管成本，而是当前由 GitHub Pages 提供服务，使用方式落在其适用范围内。未来增加服务端功能时，需要重新判断成本和托管方式。

GitHub Pages 本身有用途和使用限制，不能把当前方案直接推广为所有产品网站的通用托管方案。[GitHub Pages 使用限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)

## 制作完成后，还要维护什么

静态网站减少了服务器运维工作，但内容和页面仍然需要维护。

项目检查的重点包括：文章信息是否一致，链接是否有效，复制与下载是否对应当前正文，以及桌面和窄屏下是否能够正常阅读。

资源体积也会影响访问体验。例如，网站曾将约 1.67 MB 的头像原图转换为约 9 KB、适合实际显示尺寸的 JPEG，避免访客为一个小头像下载过大的图片。这类调整处理的是资源交付效率，不需要改变网站内容。

后续维护还包括域名到期、依赖更新和外部资源可用性。地图、统计等外部服务，也需要分别关注，不能因为主体页面是静态文件，就认为所有功能都完全独立运行。

目前，这套结构已经能够支持文章展示、内容更新和 Markdown 导出。以后如果确实需要留言、账号或多人投稿，再为这些具体需求增加服务端能力。
