从编辑到审阅：VS Code 与 Codex 的工作区布局

发布于 2026.11.22AI 辅助：GPT

关键词：VS Code　·　Codex　·　工作区布局　·　交互设计　·　任务恢复

This article is available in Chinese.

在 VS Code 里，打开终端跑一次测试，回来时还需要接着改刚才那行代码。在 Codex 里，打开差异看过几行修改，回来时更需要接着讨论刚才那项任务。两个人都离开了主区去查证据，但回来要恢复的东西不同。前者是文件、编辑组与光标所在的位置，后者是任务的目标、工作环境，以及刚刚产生判断的那处变更。主区之所以不同，是因为它们分别保管了用户下一步要用的工作现场。

仍用一个虚构的订单故障作对照。“待处理”筛选混进了“已取消”的订单，规则写在 filter.ts，状态定义在 status.ts。在 VS Code 中，使用者直接操作文件和命令。在 Codex 桌面端的本地开发场景中，使用者可以把修改委派给代理，再检查实际变更。本文讨论的是这两种工作方式怎样分配屏幕空间。产品文档能确认区域的功能与移动方式，具体位置的取舍是本文根据任务推导的设计解释。

一、先区分正在处理的对象、操作权和回程

主要对象是围绕一段工作反复被引用的东西。直接编辑时，问题最终要落实在某个文件的某个位置，排版要让人容易重新找到并操作它。委派时，一项任务可以牵涉多个文件，还可能跨几轮执行。对话需要延续的是“要交付什么、边界是什么、此前试过什么”。同一个人切到手动编辑时，文件仍然重要，只是任务对话为这些文件提供了一层共同的来路。

操作权在这里可以拆成两个问题。第一，键盘或按钮的动作交给谁。把焦点放在 VS Code 编辑器，键入内容会进入代码缓冲区；切到终端，键入会进入对应的终端会话。第二，动作最后改变什么，由谁发起、谁确认。Codex 输入框发送的是意图，在当前环境和权限允许时由代理执行文件修改或命令；审阅区中的暂存、提交等操作则有各自明确的 Git 后果。光标在输入框里，只回答了键盘去向。代理可访问的目录和用户已确认的操作，由会话环境与相应权限决定。Codex 环境模式 · Codex 本地变更审阅

回程是短暂离开当前工作后，能否带着新信息继续原来的动作。按返回键只说明视图发生了导航。看到原文件却忘了自己在对照哪条状态定义，回程依然断了。回到原任务却分不清刚才的差异来自哪轮，也会丢掉审阅的依据。真正需要设计的是离开时留住什么、回来时带回什么。例如文件和编辑位置可以留在编辑组，失败的断言带回一条新的定位。任务约束留在对话，审阅意见则带回比较范围内的一处变更。

  • 主区保留的现场。VS Code 保留打开的文件、编辑组与查看位置。Codex 保留当前任务及其要求、进展和决策。
  • 人在哪里动手。在 VS Code，用户直接编辑文件或在终端发命令。在 Codex，用户可以给代理下达要求，也可以审阅证据、追加反馈或手动接手。
  • 回去时带什么。VS Code 的终端结果可以带回文件和行的位置。Codex 的审阅反馈可以带回具体变更，同时接上原任务的约束。

这里比较的是两类工作重心。VS Code 也能审阅差异和使用代理，Codex 也能打开文件和使用终端。判断哪一块应当成为主区，要看正在分析的工作方式反复把人带回哪里。

二、VS Code 左边的两列管的是两层选择

图1　VS Code 默认工作区示例。观察最左列图标、文件树、编辑器标签三者各自改变的范围。截图复用自原文。图源为 VS Code 官方界面文档。

活动栏（Activity Bar）是工作台的一级入口。点资源管理器、搜索或源代码管理，通常会让主侧栏显示对应的视图。选“搜索”是改变找东西的方式，点搜索结果才是选择一个具体对象。切换活动栏时，编辑区可以继续显示原来的筛选函数。这种安排使用户能更换手边的工具，而不必先放下正在读的文件。活动栏的层级高，主要因为它选择的是一组工具，它只占窄窄一列，因为界面仍要把大部分编辑空间留给正在处理的内容。VS Code 活动栏 · VS Code 主侧栏与辅助侧栏

主侧栏（Primary Side Bar）是这些工具展开后的工作区域。资源管理器按路径组织项目，搜索视图按查询结果组织匹配，源代码管理按 Git 状态组织变更。一个 filter.ts 可以同时属于目录、搜索结果与变更列表。这三个入口各自回答不同的问题：它放在哪儿、哪些行符合查询、它相对当前版本改了什么。文件打开以后，编辑器标签又承担第四件事：这个文件已经被带到哪一组工作里。它和文件树里的同名项构成的是同一对象的两种参照，一边保留项目中的位置，另一边保留操作中的位置。

左边布局的理由可以从这三层的关系推出来。一级入口和它切换的视图相邻，点击后比较容易扫到变化发生在哪里。窄图标列里的项目少而稳定，旁边的内容随工具改变，可以用伸缩宽度容纳缩进、路径和文件名。把纵向目录放在编辑器旁边，会从编辑器拿走一部分宽度，却几乎可以共用整个高度。一条较深的目录因此还能保留足够多的可见行。若把整棵树搬到顶部，它仍然能导航，但展开长列表会占用代码的阅读高度或覆盖刚读过的几行。若活动栏和它切换的侧栏分居两边，选择与反馈的距离会更远，也会给另一侧原本的参照区增加变化。

左边是这套默认布局中的选择，重点是选择器和被它切换的视图保持邻接。 把两者成组移到右侧，仍然能够保留这条关系。熟练使用键盘导航的人，也可以把侧栏平时收起，搜索时再打开。反过来，如果任务每天要展开长目录，或者要持续观察搜索结果，固定占一点横向空间就有实在的用途。VS Code 提供侧栏和面板的位置调整，说明这几块有稳定的角色，也能按照屏幕尺寸和查找方式重新停靠。VS Code 自定义布局

这里还有一个容易误解的层级。活动栏图标亮起，说明主侧栏正在呈现哪种视图。文件树中某项有选中状态，说明目录里的哪个对象被选择。编辑器里的插入点，才说明下一次键入会作用在哪里。用户扫一眼左边能知道手边是什么工具，扫一眼中间能知道在编辑什么。三个状态能独立发生变化。例如打开搜索后，现有编辑器组依旧存在。区域之间正是靠这些独立状态，才可以在同一窗口里服务几件不同的事。

三、编辑器组保存两份参照关系

订单案例里，筛选逻辑中的一个状态名要与定义文件对照。假设定义存在三个相近含义的值，某一项表示已经下单但等待后续处理，另一个表示退款后恢复待处理。如果一边改条件一边反复翻定义，费力的地方是不断把眼前的行同刚记过的值重新配对。有了左右两个编辑组，可以让规则文件停在条件附近，定义文件停在枚举附近。视线短暂移过去时，两边的截取位置仍然可见，代码所表达的关系可以直接比对。

这属于认知工作怎样分给界面的例子。Hollan、Hutchins 和 Kirsh 的分布式认知研究把人、工具与外部表征一起作为分析对象。在这里，用户原本要在脑中维持“另一个文件哪几行写了什么”，并排后界面替人保留了这些可重复读取的线索。这个框架帮助解释布局的收益，具体能省多少时间还会受代码长度、屏幕宽度和操作习惯影响。分布式认知研究

Kirsh 和 Maglio 区分了两类动作。一类直接改变要交付的对象，另一类通过调整外部信息，帮助人看清问题。把两个编辑器排在一起可以放到后一类理解。它改变了条件和配置在屏幕上的参照关系，可能省掉之后好几次重新查找。这样看，新增一次“拆分编辑组”的操作也有价值。看布局的成本，应把它为后续判断省掉的工作算进去。Kirsh 与 Maglio 的认知性动作研究

编辑器组和标签的分工也因此能讲清。组是可以同时保留的几个阅读现场，标签是在每个现场里可切换的文件。两份文件放在同一组的两个标签，节省横向空间，但一次只能看一份。拆成两组则以空间换同时可见。当配置只需查一个值时，跳转一次外加可返回的导航历史往往足够。逐行比较、反复往返时，并排更能留住对应关系。屏幕窄到两列都需要横向滚动时，可靠的返回位置会比强行并排更有用。设计要找的是必须同时看见的那部分信息。两侧内容之间的关系比“两边都能打开文件”更重要。VS Code 编辑区与编辑组 · VS Code 导航历史

回程还可以拆出一项具体的验收。去看定义前，用户停在 filter.ts 的条件行。回来后，原文件、原来的编辑组、原选择或滚动附近的位置应当能重新找到。Altmann 和 Trafton 的实验表明，中断前后能重新见到任务相关线索，有助于人恢复任务。在开发工作区，这类线索可以是仍亮着的标签、原来的光标位置，也可以是编辑历史中的“后退”。它们分别帮助用户找回对象和进度。这项研究解释了为什么要保留线索，无法从中直接算出 VS Code 某种布局的收益。任务中断与恢复线索研究

四、底部面板与状态栏处在同一边，承担不同职责

底部的面板区域（Panel）可以承载终端、问题、输出和调试控制台等视图。微软的扩展 UX 指南建议，把需要较宽横向空间、用于辅助工作的视图放在这里，也提醒用户经常收起面板。这个建议给出了比“软件都习惯把工具放在下面”更直接的依据。读长命令、路径、日志或带字段的错误时，横向空间能少切断几组本来应该连着读的字符。打开面板时，它从多个编辑组下方统一借高度，通常不用继续压窄已经并排的两列代码。收起后，编辑器取回阅读高度。VS Code 面板设计指南

用订单故障看，终端在下方的作用是让执行与编写可以并存。用户能保留上方规则和配置在各自的位置，下方先跑一次针对筛选的检查，再回去改。这时终端是真实的输入区，能接收命令，也可能有进程在持续运行。回程要从输出里得到能定位的错误或可信的通过记录，还要分得出命令在哪个目录、哪一次尝试、用了什么已保存的代码。若按错误路径打开文件，界面把结果变成了下一步可处理的位置。若只留一个没有批次的绿色提示，仍然要回去找这次执行验证了什么。VS Code 终端与文件链接

底部的位置也有反面成本。日志需要持续占许多行，而编辑器正在看一个较长的调用链时，面板会挤掉重要上下文。此时移到侧面、最大化或把终端放进编辑器组都可能更合适。要决定是否常驻，看它要不要和主对象持续同步对照，以及每次展开会不会让人丢掉已有参照。要决定放底部还是侧边，看辅助视图至少需要多少宽度和高度，以及打开它时主区支付哪个方向的空间代价。VS Code 自定义布局 · 终端编辑器

Blender 的时间轴也能用同一组问题解释。它的横坐标直接代表帧，需要一定宽度来显示时间跨度与关键帧间距。用户移动播放头，会让视口展示另一帧，从而看到模型、姿态或场景在该时刻的样子。底部横条可以与上方视口并存，几何画面保留观察面积，时间信息也有足够宽度展开。VS Code 终端的横轴不编码时间，它需要宽度主要是因为行文本、路径和参数。动态的共同点在于：两种视图都能发起一次观察，并提供关联的状态或反馈；看完以后，用户仍希望上方主工作对象容易找到。可以把它们抽象成与主工作对象相邻、按需占用面积的控制与反馈区域，再根据数据和任务决定具体位置。Blender 时间轴

状态栏（Status Bar）是另一种结构。它的高度很小，负责让用户随时扫一眼当前工作环境及活动文件是什么状态。按 VS Code 官方指南，工作区范围的状态项通常在左侧，例如分支、同步或问题概况，活动内容相关的项通常在右侧，例如语言模式、缩进或编码。有些项目能点击并切换设置，其入口仍然围绕一项已经展示出来的状态。在编辑或打开工具时，状态栏处于稳定的窗口边缘，适合短暂确认；在光标旁常驻同一组信息，会反复切进代码阅读。具体执行记录、长错误和能定位的问题仍然有自己的面板或编辑位置。底部面板借来一段空间做工作，状态栏用很薄的边缘持续告知当前环境。VS Code 状态栏设计指南

五、Codex 中央持续保留任务，右侧按证据展开

图2　Codex 桌面端任务审阅关系示意，复用自原文。左侧选择任务，中央保留任务经过，审阅视图展开代码证据。图中的布局、文件和订单数据用于解释关系。

左侧提供任务索引。 修筛选和改列表样式是两项可以分别开始、暂停和重访的工作。列表主要需要表达任务叫什么、归于哪个项目、哪件事还值得查看。它允许用户用很小的一块面积切换整段上下文。VS Code 里点活动栏图标通常只是更换侧栏工具，Codex 里点另一个任务往往会进入另一段历史，两者的点击范围不同。对布局的要求也不同：切换任务后，需要有足够明确的任务身份。涉及同名项目或同名文件时，工作环境也是身份的一部分。单凭任务标题只能知道正在讨论什么。ChatGPT 桌面端 · Codex 环境模式

中央同时放任务经过和下一次输入。 用户提交筛选故障时，可能只要求修规则。执行中发现状态配置分为历史订单和当前订单，用户又补充“先保留历史语义”。之后的一轮修改要同时参照最初目标和这条新约束。滚动的对话把要求、追问、执行记录和决定按发生关系留在一处，靠近阅读末端的输入框承接下一步。这个布局允许任务定义在过程中逐渐变得精确。若把中央始终让给某个文件，后来者要从文件猜改动缘由，或另开线程拼回那次范围决定。对话占据中央的价值，就在于使多文件、跨轮次的工作拥有一个能持续接上的对象。

对话和代码差异还各自使用不同的阅读顺序。要理解任务为什么改口，可以沿消息先后看。要理解筛选规则改了哪几行，则要按仓库、文件和代码位置检查。假设任务前后两轮都改过 filter.ts，旧消息中的代码片段仍属于当时的交代，最新差异表达的则是当前选定范围内的 Git 变化。如果把差异完整塞进每一轮消息，历史里的几份代码都能读，却需要先判断哪份是要审核的版本。如果中央只留下最新差异，任务之前定过的条件又不容易追溯。两种材料各有可重访的位置，审阅时可以让目标和证据并存。

右侧摘要与具体审阅分两层。 摘要给人一个轻量入口，知道当前有变更可以检查。进入差异之后，使用者才需要足够的面积阅读文件、上下文和删改行。两个层次的显示成本不同。任务正在执行或一句话能交代清楚时，摘要可以占很少的空间。到需要逐行审阅时，右侧展开可把任务目标留在可见范围。大范围修改或窄屏上，证据可能更适合暂时占主屏，专门留一个明确的返回任务入口。侧边位置适合频繁对照，能否在展开、全宽、收起之间保存现场，决定了布局能不能用于不同屏幕。Codex 本地变更审阅

这些安排与任务委派的工作方式有关：人与代理需要反复对齐目标和交付物。它可以解释为何要给对话一个稳定的大区域，并把证据做成可按需展开的视图。它还推不出审阅区必须在右边。把证据放进可返回的独立标签也能建立联系，只是经常比对时要重新切换阅读现场。把证据长期贴在右边，则会持续挤压对话与代码的宽度。布局取决于两份内容是否要经常并看，和切换后能不能把人带回正确的位置。

六、操作权怎样从执行结果回到人手上

VS Code 的直接编辑里，错误路径可以把用户带到某个文件及行列。用户从那里判断是改断言还是改规则，再自己输入。这里的回程主要是让信息落到原本就能动手的地方。需要保存的还包括原来的编辑组和参考文件。只把错误位置打开，却覆盖了正在比较的另一份定义，可能办完定位这一步，又破坏了接下来用于修正的参照。

Codex 的任务审阅多出一层范围判断。官方说明，工作区的审阅面板可以显示未暂存、已暂存、选定提交、分支对比和最近一轮等范围。假如用户此前手动改过 filter.ts，代理又在同一文件里修筛选，未暂存视图能同时出现两个人的编辑。切换比较范围时，文件名字可能完全相同，但差异中的行代表另一组变化。对话身份回答“我在审哪个任务”，审阅范围回答“我眼前比较的是哪批变化”。 两项都需要有清楚的落点，邻接关系无法替代它们。Codex 审阅范围

这也说明为什么独立审阅区要提供自己的范围和动作。用户可以继续就某一行向代理提出具体要求，也可以手动暂存、取消暂存或撤回部分改动。它们分别改变任务意图、Git 暂存区或工作树。若把这些动作揉成一个含义模糊的“接受”，用户会难以预料接受的是某段建议、某个文件，还是整组变更。任务对话中的一句“改得可以”，在交互层上与点击暂存或推送需要有不同结果。做可委派的工具时，设计上要把确认、反馈和对产物的直接处理各自落到具体对象上。Codex 暂存与撤回

有价值的回程发生在审阅者点击了某处变化之后。比如他选中筛选条件附近的一行，说明“保留退款恢复为待处理的分支”，再回对话要求处理。行内反馈保存了争议出现的位置，对话补充本轮希望完成的动作与边界。OpenAI 的文档也要求留下反馈后回到对话明确提出下一步。下一次审阅时，文件可能改动、行号可能移动，用户需要重新核对那项语义要求和当前变更。这样的循环让反馈可以跟着产物往返，用户也能在不同回合区分哪些是看到的、哪些是要求做的。Codex 行内反馈

运行证据也适合同样处理。对话里的“通过”通常是可快速读过的摘要，终端结果可以提供命令、输出与执行条件。二者结合，能把“允许继续”的判断连回一次可辨认的运行。对于同一个目录里同时开的两项任务，记得哪项任务说过“通过”还不够。要判断是否覆盖了取消订单，需要知道那次运行针对哪个目录下的哪份修改、实际验到了什么。证据少量时，在任务消息里保留命令和关键结果很有用。日志很多时，给摘要一个入口，把详细输出留在可展开的地方，能保持对话可读。Codex 的项目终端还能让用户亲自复验，它仍然有独立的输入焦点和会话。Codex 集成终端

七、从工作流推到布局，先确定四条关系

把一次跨区操作拆开看，能看见对象、位置和证据分别在哪一步起作用。对象是被引用的东西，位置是能够定位它的地址，证据是让人相信下一步有依据的记录。 文件可以同时出现在树和编辑器，因为用户既要知道文件属于哪个目录，也要在操作时回到某一行。差异可以同时有摘要和展开视图，因为读取进展与核查变更需要的数据量不同。只有保留正确的地址和来源，用户才能把一边得到的信息用到另一边。

  1. 选择器挨着被它切换的区域。切换频繁时，用户需要马上看见哪一处变化。活动栏与主侧栏相邻，就是这种关系。
  2. 稳定保留一个主要工作区。如果每次查阅或执行后都要回来继续，主区就要能保留工作现场。VS Code 的编辑器组留住文件位置，Codex 的任务对话留住目标与约束。
  3. 把反复比较的内容摆在一起。一次判断如果依赖两处信息，就让它们能同时出现，例如筛选规则和状态定义，或任务约束和代码差异。
  4. 让反馈带着地址回来。当结果会影响下一步，连接就要带上具体对象，例如终端路径指向编辑器中的一行，审阅意见指向任务的一处变更。

把这几条用在新工作台上，一次具有真实分支的任务就能先排除一些布局。假如主区是项目文档，右侧展开放的是同一文档的审批记录。用户切换另一份文档时，审批记录通常应该随文档切换。如果用户正在比较两份历史版本，则需要独立固定一份参照，并明确它还属于原文档。两种行为都能画在同样的右边，但要保留的状态正好不同。这个区别得先在交互上讲清，再去决定面板有多宽、是否常驻。

再回到订单故障，可以用三个具体变化检验一份原型。第一，现有代码保持打开，切换左侧工具，看用户能否分清是在换查找方式，还是换了编辑对象。第二，打开下方的结果，故意给出两个有相近文件名的运行记录，看用户是否能找到当时运行的目录和需要回去的代码位置。第三，切回另一个 Codex 任务，观察是否能看懂眼前差异具体属于哪个比较范围，并准确回到尚未处理的那条意见。记录反复搜索、恢复位置和选错对象的时刻，就能知道应调整的是区域的位置、信息来源的显示，还是跨区动作要携带的数据。

理论和产品观察在这里各做一件事。分布式认知解释了界面为何值得替人保存参照。任务恢复研究解释了为何返回时还应保留线索。VS Code 和 Codex 的实际设计，则让人看到参照与线索具体长什么样。沿着这些关系先能确定区域角色，再用几种布局与真实任务验证宽度、高度和常驻方式。这样需要反复试的，是有限的空间取舍，主要对象和操作后果已经有了依据。
